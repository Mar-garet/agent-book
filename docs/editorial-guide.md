# 写作与研究约定

本书要帮助读者形成判断：当任务、环境和限制发生变化时，能够解释一种 Agent 设计为什么成立，以及它会在哪里失效。

## 每章从一个具体困难开始

先把读者放进情境，再给机制命名。例如，先让一个任务中断，再解释检查点；先让一次写入返回超时，再解释幂等；先让模型记错项目规则，再解释记忆的更新与失效。

术语第一次出现时用中文解释。读者应当先理解谁在做事、信息怎样流动，再接触工具名、协议名和实现文件。

## 用同一组问题比较项目

每轮研究先确定场景、任务、版本和配置，再追问：谁决定下一步，谁执行动作，状态保存在哪里，工具怎样暴露，权限在哪里检查，错误怎样返回，怎样恢复，如何判断完成。

不能因为一个运行系统内置了某项功能，就推断使用框架的人无法实现同样的功能。也不能因为框架可以扩展，就宣称它开箱即用地解决了全部问题。

## 给不同强度的结论不同写法

**材料支持的事实**需要指向固定版本中的文档或源码。README 能证明项目如何描述自己；实际调用顺序、默认配置和异常行为，通常还需要继续看实现。

**设计推断**需要写清前提。例如，“默认工具更少可能降低选择负担”是推断；它是否改善某项任务的成功率，需要实验。

**实验结论**必须保留任务集、模型、配置、重复次数、原始轨迹和统计口径。没有运行记录时，只能提出实验方案。

对某项能力尚未找到证据时，写“本轮未核对”，不要写“不支持”。

## 让源码成为论据

正文先给读者一个可以理解的过程，证据链接放在论断附近或章末。避免连续罗列类名、内部路径和配置项。需要展示框架入口时，明确哪些是真正由调用者触发的入口，哪些是请求数据、业务适配器和支持基础设施。

引用上游材料时优先使用自己的解释，保留原作者的出处，少量摘录才使用引号。源码快照由 Git 子模块和 SOURCES.json 共同记录；在线文档需记录查询日期，避免把后来更新的网页当成旧版本行为的证明。

## 后续深化顺序

先逐项验证代表案例的关键执行链，再扩展到其余项目。优先补工具错误传播、上下文压缩的信息损失、记忆冲突处理、恢复后的副作用重复，以及多 Agent 的结果汇总。

每完成一个项目的研究，应让某个主题章节更具体。研究记录可以逐项目保存，正文仍围绕问题组织。
