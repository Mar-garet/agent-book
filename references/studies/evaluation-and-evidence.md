# 怎样判断任务完成：从测试通过到业务验收

> 研究与查询日期：2026-10-17。\
> 方法：浏览原始 SWE-bench、原始 τ-bench 论文与官方历史仓库，追踪任务、运行与验收的关系。没有运行这两个基准，没有调用模型，不引用最新榜单，也不报告任何模型成绩。\
> 论文固定为首次发布版本：SWE-bench `arXiv:2310.06770v1`（2023-10-10）；τ-bench `arXiv:2406.12045v1`（2024-06-17）。仓库引用固定历史提交，避免把后续实现当成原始实验设置。

## 一、先把完成声明交给谁检查讲清楚

本书 [报表案例](../../book/00-do-you-really-understand-agents.md) 已经出现一个反例：平台显示重跑成功，产物却缺少最后一天。对这个案例，任务准备者应当先写明环境、日期范围、允许操作与验收条件；Agent 负责调查和行动；工具执行具体操作；验收程序检查外部状态和产物；业务人员处理仍需判断的口径与取舍。

**设计推导：** 模型最后说“已完成”，只能证明它生成了这句话。工具返回成功，通常只说明该工具认可本次请求或某个执行阶段。任务是否满足目标，要由事先定义的完成条件判断。不要让同一句自然语言同时扮演请求、执行记录和验收证明。

```text
任务准备者固定输入、初始状态、授权范围与预期结果
→ 运行系统按指定配置启动 Agent
→ Agent 提出动作，工具执行并留下记录
→ 验收程序读取实际结果与必要的过程记录
→ 逐项判定：满足、未满足，或信息不足
→ 研究者汇总全部运行，包括失败与人工介入
```

这是一条本书建议的责任链，不是说所有基准都采用完全相同的实现。

## 二、SWE-bench：补丁能应用，还必须真的修复并保持原有行为

**材料事实 S1：** 原始任务来自真实 GitHub issue 与相关修复 PR。任务向模型提供问题描述与代码库快照，要求模型生成代码修改；验收执行修改后的测试，不要求生成内容与参考补丁逐字相同。原始论文的基线还研究了检索哪些文件作为上下文，并非规定所有参与系统必须采用一个固定的自主 Agent 循环。[论文 v1，第 2 节与第 4 节](https://arxiv.org/pdf/2310.06770v1#page=3)

具体运行时，评测程序重置任务环境，处理预测补丁，安装任务所需环境，应用基准的测试修改与预测修改，再运行测试。补丁应用失败与测试阶段失败，都可能阻止任务得到完整的成功判定；“生成了一个 diff”不是验收终点。[历史执行器](https://github.com/SWE-bench/SWE-bench/blob/b8299951846f4b6ef23176f8c137cffda79bc747/harness/engine_evaluation.py#L95-L127)

**材料事实 S2：** 评测区别两类关键测试：`FAIL_TO_PASS` 是参考修复前失败、修复后通过的测试，检验问题是否得到解决；`PASS_TO_PASS` 是原本通过且应继续通过的测试，检验原有行为是否得到保持。历史判定函数只有在两类通过比例均为 1 时返回完整解决。[历史完成判定](https://github.com/SWE-bench/SWE-bench/blob/b8299951846f4b6ef23176f8c137cffda79bc747/metrics/metrics.py#L78-L95) [论文 v1，附录 A.4](https://arxiv.org/pdf/2310.06770v1#page=20)

**设计推导：** 报表助手也需要同时回答两个问题：缺失日期是否补齐，以及已有日期、汇总口径和访问范围是否保持正确。只盯着原来失败的那一处，容易把“修好一个错误，同时引入另一个错误”当成成功。

但这些检查足以判定的是**基准规定的测试是否通过**。若测试没有覆盖权限、隐私、性能或某项业务规则，不能自动宣布这些性质也得到证明。迁移到本书案例时，业务验收者仍要明确哪些目标已被检查，哪些尚未覆盖。这是对验证范围的推导，不是对 SWE-bench 任务质量的整体结论。

## 三、τ-bench：对话可以不同，最后改变了什么仍应可检查

**材料事实 T1：** 任务准备者提供数据库、API 工具、领域政策和带预期结果的任务；用户模拟器持有任务意图，与 Agent 分步对话，Agent 通过工具读取或修改状态。任务标注不直接交给 Agent 当答案。原始设计通过限制任务歧义，使允许的目标数据库状态可被确定。[论文 v1，第 3 节](https://arxiv.org/pdf/2406.12045v1#page=3)

历史实现每次重置环境时复制初始数据库。验收先记录 Agent 结束后的数据库摘要，再从相同初始数据出发执行标注动作，计算目标摘要并比较。它检查最终状态，因此并不要求每一个读取动作与参考轨迹完全相同。[历史环境重置](https://github.com/sierra-research/tau-bench/blob/6f4b718037db619539b8b692060e6686f3f0dcc9/tau_bench/envs/base.py#L59-L69) [历史状态验收](https://github.com/sierra-research/tau-bench/blob/6f4b718037db619539b8b692060e6686f3f0dcc9/tau_bench/envs/base.py#L107-L149)

**材料事实 T2：** 奖励还可以要求 Agent 向用户提供必要信息。历史实现针对任务列出的输出，检查它们是否出现在回复中，比较时忽略大小写并移除回复中的逗号；它不是一个通用的语义真实性证明器。[历史输出检查](https://github.com/sierra-research/tau-bench/blob/6f4b718037db619539b8b692060e6686f3f0dcc9/tau_bench/envs/base.py#L119-L134)

原始论文明确承认：规则奖励为成功，仍可能不足以证明整个服务过程成功。例如最终退货状态正确，Agent 却没有先取得政策要求的用户确认。最终状态与回复检查没有穷尽过程要求。[论文 v1，第 3 节奖励边界](https://arxiv.org/pdf/2406.12045v1#page=4)

**设计推导：** 对报表任务，最终文件完整与操作过程获得授权应分开验收。相同文件可以由“在测试环境按许可重算”得到，也可以由“越权修改生产配置”得到。比较产物无法区分这两条路径，需要记录授权与写入发生的先后关系。

同样，真实业务可能允许多种正确结果，而原始 τ-bench 刻意安排唯一目标状态。本书不能直接要求每个真实任务的产物与某一个参考文件逐字一致。更合适的做法是预先写出允许结果必须满足的条件，例如日期覆盖完整、汇总与明细一致、未写入生产环境。

## 四、多试几次找到答案，与每次都可靠，是两种问题

先假设每次尝试都从相同任务条件重新开始，沿用同一套系统配置，且试验之间不共享上次结果。论文把这种设置表达为独立同分布尝试；它不等于让一个不断累积经验的会话继续重试。

原始 τ-bench 对两个指标作了明确区别：[论文 v1，第 3 节](https://arxiv.org/pdf/2406.12045v1#page=4)

| 指标 | 它问的问题 | 更接近的使用情境 |
| --- | --- | --- |
| `pass@k` | 同一任务独立试 k 次，至少一次成功的概率，再按任务汇总 | 可以尝试多个候选，并另有办法选出正确结果 |
| `pass^k` | 同一任务独立试 k 次，每次都成功的概率，再按任务汇总 | 用户反复遇到同类任务，需要结果持续可靠 |

**设计推导：** 系统可以很擅长“多次尝试中偶尔找到正确补丁”，却不适合每天无人值守地完成一次报表。反过来，`pass@k` 高也没有证明系统能自行识别、挑出那次正确结果；挑选过程需要自己的验证依据。

这里的 k 是指标观察的尝试组大小，收集的每任务样本数 n 可以更大。报告应说明 n、k 和估计方法，而不是拿一条挑选后的成功轨迹充当重复可靠性。也不能把跨任务总体平均成功率直接连乘，冒充先按每个任务估计再汇总的结果。这些都是解释指标时需保持的统计边界，本文不计算任何实际成绩。

**材料事实 T3：** 原始运行器按 `num_trials` 重复任务，为每次任务创建独立环境和 Agent，并保存任务 id、trial、reward、info 与完整消息轨迹。异常也会留下 reward 为 0 的记录和错误信息，而非只输出成功对话。[历史运行与记录](https://github.com/sierra-research/tau-bench/blob/6f4b718037db619539b8b692060e6686f3f0dcc9/run.py#L19-L91)

**设计推导：** 如果把失败后的人工修改、模型更换或预算扩充悄悄合并到同一组重复运行，就已经改变了试验条件。它可以作为另一种有人协助的系统测量，但应独立标注。

## 五、哪些条件没有固定，两个数字就不能直接比较

以下是本书的评测记录建议。它们用于说明一次结论覆盖哪些条件，不是宣称两个基准已经采用完全相同的记录格式。

- **任务与验收。** 固定任务 id 清单、初始快照、用户要求、数据范围和验收程序版本。说明分母是全部任务、实际提交的任务，还是已经成功完成验收的子集。
- **模型与上下文。** 记录具体模型标识、提供商与运行日期，以及系统提示、检索材料、压缩策略和记忆初始状态。使用人工选出的相关文件，必须披露这种信息优势。
- **工具与外部服务。** 固定工具 schema、实现版本、权限和模拟数据。工具的同名并不保证同一能力与失败语义。
- **预算与重试。** 记录模型调用、工具动作、token、耗时上限及每种重试规则。多次候选生成和筛选消耗的资源也属于系统的一部分。
- **交互者。** 若用户由模型模拟，记录其模型、提示和采样设置；若是真人，说明任务分配、允许提示和中途协助规则。
- **人工干预。** 保留人工补输入、修改状态、挑选候选、修补环境与中止任务的记录；区分事先准备任务和运行中替 Agent 决策。

这些差异有直接的材料依据。SWE-bench 原始论文区分普通检索与由参考修改选文件的 oracle 设置，并指出后者提供了实际解决问题时未必拥有的信息。[论文 v1，第 4.1 节](https://arxiv.org/pdf/2310.06770v1#page=4) τ-bench 的历史 GPT Agent 每次运行最多循环 30 步；用户模拟器又使用不同的采样温度。只固定 Agent 模型名，仍不足以固定整个交互系统。[历史 Agent 循环](https://github.com/sierra-research/tau-bench/blob/6f4b718037db619539b8b692060e6686f3f0dcc9/tau_bench/agents/gpt_function_calling_agent.py#L76-L117) [历史用户模拟器](https://github.com/sierra-research/tau-bench/blob/6f4b718037db619539b8b692060e6686f3f0dcc9/tau_bench/envs/user.py#L69-L83)

**不可比较的情形示例，均为假想：** 一边只有一次尝试，另一边试到成功；一边仅获得任务描述，另一边由人给出根因；一边在完整任务集验收，另一边只统计能成功启动环境的任务；一边用冻结模拟工具，另一边连接会变化的真实服务。可以报告各自观察，但不能把差距全部归因给 Agent 框架。

## 六、失败轨迹要能回答下一次该改哪里

历史 τ-bench 已把结果与逐轮轨迹放在同一条运行记录中；SWE-bench 的历史评测说明也把模型预测、任务数据与日志目录分开配置。[τ-bench 记录字段](https://github.com/sierra-research/tau-bench/blob/6f4b718037db619539b8b692060e6686f3f0dcc9/run.py#L51-L86) [SWE-bench 评测参数](https://github.com/SWE-bench/SWE-bench/blob/b8299951846f4b6ef23176f8c137cffda79bc747/harness/README.md#L11-L22)

**本书建议：** 在汇总成功率前，先保存每次运行的输入快照、模型实际可见材料、动作参数、工具结果、状态变更、最终产物和逐项验收结论。定位失败时，依次检查：

1. 任务是否清楚，验收器是否真的检查了目标；
2. 运行环境是否建立成功，所需材料是否进入上下文；
3. Agent 是否选对动作、填对参数并完成全部子目标；
4. 工具是否执行了动作，返回是否代表最终完成；
5. 产物是否满足要求，过程是否满足授权和禁止事项；
6. 对外完成声明是否与实际结果一致。

这是故障分析顺序，不是原始基准自动输出的一套统一分类。环境故障、工具超时、Agent 推理错误与验收器缺陷应留下独立标记；公开某个总分时仍需遵守声明的评分口径，不能通过删除不利样本悄悄改变分母。无法确认是否完成时，保留“信息不足”，不要填成已成功。

## 七、接到报表案例：把离线检查与有模型任务分开计数

本书已完成一组应用离线验收检查；有模型参与的端到端报表任务仍未执行。两者需要分别计数。

先由任务准备者冻结一份测试环境快照，写明日期范围、目标报表、允许的验证动作与禁止修改的生产对象。再由验收程序直接读取最终产物，检查日期覆盖、汇总与明细一致、异常是否说明，以及动作记录是否超出授权范围。目标与环境由准备者固定，结果由验收程序判断，Agent 不能仅靠修改自己的完成文字通过验收。

**第一组：不用模型的验证器检查。** [实际脚本](../../experiments/task_acceptance.py) 使用九个构造样例，涵盖完整产物、缺失日期、错误数值、错误环境、未获准写入、旧任务产物、产物缺失、排队与远端仍运行。它检查本书所写的应用规则，结果见 [离线记录](../../experiments/results/task-acceptance.json)。输入记录被假定可信，业务条件也仅覆盖本组约定；通过检查不能推导 Agent 会自动完成任务。

**第二组：模型参与的端到端任务，尚未运行。** 在冻结环境里让 Agent 从用户请求开始调查、行动、验证和汇报；对每个任务按相同配置重复运行，保留失败与人工介入。分别报告独立运行数量、满足验收的数量、预算、越界动作、信息不足与异常原因。只有这一组才支持在声明条件下讨论任务完成率与重复稳定性。

两组应当各有自己的分母。浏览器检查、链接检查、固定响应下的恢复实验，都是有价值的工程检查记录；它们不是新增的模型任务成功样本。即使采用固定模型响应模拟工具规划，也只能证明该输入下运行系统的行为，不能与真实模型决策混计。

进一步可以设计三个反例：工具报告执行成功但产物缺日期；产物完整但修改了禁止对象；验收正确拒绝，Agent 却仍声称已完成。它们分别检验工具反馈、业务/授权条件，以及对外声明与实际结果的一致性，均不应只靠同一个自然语言评委笼统打分。

## 从局部检查回到任务交付

工具成功与任务成功、一次找对与重复可靠、规则验收通过与业务目标充分覆盖，分别回答不同问题。原始论文提供了可学习的评价结构，没有替本书的报表助手提供模型成绩，也没有消除真实任务中仍需人工判断的部分。

[评测系统](../../book/22-evaluation-and-completion.md) 将这些区别连到贯穿全书的报表案例；[实验目录](../../experiments/README.md#产物与过程的离线验收) 说明应用检查怎样复现。
