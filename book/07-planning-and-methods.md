# 第七章：规划与方法——下一步由谁决定？

助手开始排景点：周六上午西湖，下午去另一处参观，晚上入住。写到最后才发现，原先看中的房间那晚不可用。

它可以只换一家酒店，也可能因此需要改车次和游览顺序。计划的作用，是让这些相互影响的事情看得见；计划不能要求世界照着它发生。

## 先确认会影响后面的事情

这次两天旅行，往返交通和一晚住宿会决定剩下的时间与钱。先确认这些，再排景点，比先把每小时填满更稳妥。

但确认交通之前，未必能写出所有查询。发现到站太晚，就换一班；发现酒店太贵，就扩大位置范围；如果所有可接受住处都超预算，就把困难说明白，而不是继续假装已经排好。

ReAct 这类方法强调的，就是让行动带回的新发现改变后续判断。值得记住的是“查了以后再决定”，而不只是一段固定的提示格式。

重复查询同一家满房酒店，既没有新信息，也没有改变条件，就没有推进任务。每次查询最好能回答一个尚未解决的问题。

## 计划应该能修改，也应该留下修改原因

一份可用的短计划可以是：先查往返高铁，再找一晚安静住处，接着安排景点与餐饮，最后检查总价和周日返程。

新发现可能改变顺序。去程已经确定，酒店却没有合适候选时，可以先多查住宿，不必机械地进入下一步。

程序应保留当前选了什么、哪部分仍在找，以及为什么放弃旧方案。否则换会话时，模型可能又把已经否决的酒店当作首选。

计划保存的是当前打算。只有实际查询和检查结果，才能说明某一步已经完成。

## 哪些交给模型，哪些写成程序规则

先看车次还是住宿，可以让模型根据新信息选择。不订票、不订房，以及发草稿前检查往返和总价，就不适合每轮重新猜。

开发者可以把后几条写成程序必须经过的步骤。模型在查询阶段灵活找资料，草稿写好后，程序按明确条件检查；不合格就退回补充。

LangGraph 用节点表示步骤，用保存的状态表示进度。Microsoft Agent Framework 的 Workflow 会把消息交给相应步骤处理，并在规定位置保存进度。它们帮助开发者把顺序写清，具体检查内容仍要自己定义。

这样做少了一些自由，也增加开发维护工作。换来的好处是，模型即使急着结束，也不能跳过返程检查。

## 别把几种选择混成一个“规划模式”

计划是提前写长一点，还是每次查完再补，是一个问题。由模型决定下一步，还是程序规定先后，是另一个问题。一个助手独立完成，还是分给其他助手，又是第三个问题。

它们可以组合：程序规定最终检查，模型决定查询顺序，两个助手分别看交通和住处。没有必要为了选其中一种，就把另外两种都绑定进来。

## 什么时候值得增加专门的规划步骤

任务只有一次明确查询时，先让模型写一整页计划往往多余。任务有许多依赖、需要接手或会持续较久时，明确计划才更有帮助。

Aider 的 Architect 先写修改方案，再交给 Editor 执行，展示了“先想怎么做，再做”的分工。CrewAI 可以显式加入规划器；smolagents 还可以按间隔重新规划。这些安排都多了模型请求或交接，收益需要抵过新增工作。

对这次旅行，先维护一份短计划就够了。查询越积越多时，再决定是否需要专门整理，不必一开始把所有机制都装上。

## 等待用户，也是计划里的一种结果

如果你要求周日上午必须在上海，而现有安排没有合适返程，助手应说明冲突，询问可以调整哪一项。继续生成更多景点，并不能解决时间不够。

等待时要留下已经查到什么、还缺什么、用户需要决定什么。这样再次继续时，不必重读所有网页或重新解释整个任务。

助手现在知道先抓住交通与住宿，计划也能随查询结果修改。接下来可以让它复用读网页的方法，或者请另一个助手帮忙查一部分资料。
