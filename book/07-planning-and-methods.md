# 第七章：规划与方法——下一步由谁决定？

助手已取得 R42 的日志，并记住了业务日期与时区。错误 E42 把注意力引向字段映射，可配置版本 v6 和源分区尚未核对。此时就安排“修改配置、重跑验证”，会把线索过早变成结论。

计划应该细到什么程度？先列出完整步骤、逐步查询，或者遵循固定流程，都可能有用。选择取决于：哪些事情已经知道，哪些必须行动之后才知道。

## 在反馈中推进：ReAct 带来的视角

ReAct 的研究把推理与环境行动交替组织起来，让行动带回的新观察继续影响后续判断。这里值得抓住的是决策与反馈之间的关系，而不只是某种提示词格式。[原始论文](https://arxiv.org/abs/2210.03629)

在 R42 的情境中，助手怀疑字段映射不匹配，就应核对 run-807 实际使用的 v6 配置。如果配置与预期一致，还要查源分区，而不是因为已经写下修复步骤就继续修改。每一轮行动都应该区分某个尚未排除的可能。

如果系统连续重复同一个查询，获得相同结果，却不改变任何假设，那么循环虽然仍在运行，任务却未必在推进。可以记录当前假设、此次查询要区分什么，以及结果支持了什么。

工程实现可以记录决策摘要与行动依据。外部检查仍要落在实际动作、观察和任务状态上。

## 先规划后执行：把全局目标留在眼前

任务较长时，计划有助于表达依赖、分工和完成条件。例如，必须先确认受影响日期，才能决定重新运行范围。

但计划是依据某一时刻的信息制定的。它应当有版本、当前进度和修订理由。发现新限制后，系统需要决定修改计划、补充调查，还是请求使用者判断。

把计划当作可更新的状态，可以帮助接手者理解当前意图。把计划只保存在一段很早的回复中，则会增加后续恢复和同步的困难。

## 用程序确定结构：把稳定的要求固定下来

有些顺序不适合让模型每次重新发明。例如，确认环境后才能开放修改，修改后必须进入验收，验收失败不能直接宣布成功。

开发者可以用程序或状态图固定这些转移，再把诊断与探索留给模型。LangGraph 是研究这类有状态执行结构的一个案例，但使用图结构本身不会自动验证业务结果。[参考 L01](../references/evidence.md#l01-langgraph-的执行状态)

对于 R42，可以固定“核对任务身份 → 调查 → 测试验证 → 交付”这几个阶段，让模型在调查阶段选择查询顺序。这样不必预写每一种故障，却要由开发者维护关键状态和转移条件。

## 这些方法可以放在不同的轴上

“先规划还是逐步探索”讨论决策时间。“模型还是程序控制转移”讨论控制权。“结构化参数还是代码行动”讨论动作表达。“一个 Agent 还是多个 Agent”讨论工作组织。

它们可以组合。例如，程序规定阶段，模型在诊断阶段反复查询；系统把一个独立子问题交给子 Agent；子 Agent 用代码组合读取工具；结果返回后再更新计划。

| 比较维度 | 选择的一端 | 另一端 | 主要影响 |
| --- | --- | --- | --- |
| 规划时间 | 每步结合观察决策 | 提前形成较长计划 | 适应变化与全局协调 |
| 控制权 | 模型选择后续动作 | 程序固定关键转移 | 探索空间与执行约束 |
| 动作表达 | 单次结构化调用 | 一段可执行代码 | 组合效率与执行复杂度 |
| 工作组织 | 一个连续上下文 | 多个协作上下文 | 信息共享与隔离成本 |

这张表是本书的分析框架，不是对所有项目的分类定论。

## 什么时候值得做计划

任务具有依赖关系、需要交接、执行较久或涉及多个产物时，显式计划可能更有价值。对一个已经确定参数的单步查询，完整规划流程可能增加额外开销。

Pi 的材料说明，它将一些计划和子 Agent 工作方式留给扩展；Deep Agents 则提供更多长任务默认机制。由此可以提出比较问题：默认机制在什么任务长度与复杂度下开始带来收益？这需要实际测量，不能仅凭功能多少判断。[参考 P01](../references/evidence.md#p01-pi-的默认取向) · [参考 L02](../references/evidence.md#l02-langchain-生态层次)

## 计划需要容纳“暂时不能继续”

一个完整的执行方法需要表达等待、取消、失败和交接。模型遇到缺失凭证时，继续生成更多步骤不会产生新的访问权限。

系统应当保留已经确认的事实、仍缺什么，以及谁能够解除阻碍。这样，等待用户也可以成为清晰、可恢复的任务状态。

R42 现在有了可修订的计划，诊断仍保留探索空间，测试和交付则有固定关口。团队若想把这套做法用于下一次排查，或让两个助手同时调查，还得把经验和分工变成明确的工作约定。
