# 第十章：把项目放在同一张问题地图上

旅行助手的初稿漏掉了周日返程。问题找到了，接下来该怎么改？换一个模型？加一个检查步骤？还是换一套框架？

如果团队马上开始比较“哪个项目功能最多”，讨论很快就会变成报名单。大家都说支持工具、记忆和多 Agent，听起来差不多，真正需要自己做的工作却可能相差很大。

我们换一种问法：**为了让这个助手把两天行程安排好，哪些事希望项目替我们做，哪些事愿意自己写？**

## 先弄清拿到的是成品，还是搭建工具

现成的 Agent 应用像一间已经布置好的工作室。模型怎样接收消息、工具怎样调用、会话怎样继续，项目已经作了不少决定。Codex、Gemini CLI 等编程助手属于这类讨论。它们面向编程任务，研究它们能学到运行方法；这不表示拿来就能变成旅行产品。

框架更像搭建工具。它帮助开发者连接模型、工具和消息，但“允许查酒店，不允许订酒店”仍要由开发者安排。OpenAI Agents SDK、PydanticAI 等各有自己的组织方式，不能因为调用代码很短，就认为剩下的工作都有人做好了。

还有些项目主要组织步骤。例如，LangGraph 可以把“查资料、等用户确认、检查结果”写成一张执行图。图里的每个节点是一段程序，连线说明接下来可以走到哪里。Deep Agents 则在相关基础上组合文件管理、历史整理和子任务等机制。

MCP 又是另一回事：它约定应用怎样发现和调用服务。酒店服务使用 MCP，不会因此自动知道用户预算，也不会替应用决定什么时候可以下单。

比较之前先分清这些层次，才能算清开发者还需要补什么。

## 哪些步骤让模型想，哪些步骤写死

查交通时，助手可能先找早班车；早班车不合适，再换时间；时间仍不合适，才考虑改游玩顺序。路线会随查询结果变化，事先很难把每个分支都写完。

这适合让模型一边看结果，一边选下一步。Pi 提供较小的核心循环；LangChain 的 Agent 构建机制等也能安排模型与工具反复往返。应用仍要给它合适的工具和停止条件。

但“不经同意不能下单”不必让模型每次重新思考。程序可以直接不提供下单能力，或者在执行前检查用户批准。“行程缺一天不能发给用户”，也可以成为固定检查。

LangGraph、Agent Framework 的工作流适合表达这种必须遵守的顺序。代价是开发者要维护每个步骤，以及查不到资料、用户拒绝或程序出错时往哪里走。

Aider 还提供了另一种值得借鉴的分工：先讨论修改方案，再进入实际编辑，并把检查错误交回去继续改。它用于代码任务，但“先想清楚，再动手”的安排也提醒我们：并非每一步都需要同时开放给模型。

旅行助手可以采用一个混合方案：查资料的顺序交给模型，是否允许下单、行程是否齐全由程序检查。选择框架时，先看这种分工是否容易表达。

## 现成机制越多，要自己理解的约定也越多

只查车次和酒店时，自己接两三个工具也许就够了。助手开始处理长网页、保存偏好、分派子任务之后，逐项接起来会越来越费事。

Deep Agents 提供更多长任务机制，OpenClaw 和 Hermes 则把长期使用时的文件与记忆安排进自己的运行方式。采用这些现成安排，可以少做一部分连接工作。

不过，名字里写着“有记忆”，不等于当前配置已经启用。Deep Agents 的记忆和 Skills 受配置与存储后端影响；Goose 的记忆可以来自可选扩展；Agno 的记忆更新也有启用条件。选中项目之后，还得弄清自己实际打开了什么。

少一点默认机制，通常更容易看清每步在做什么，但缺的部分得自己补。多一点默认机制，可能更快搭出完整功能，但也要花时间理解它们怎样配合。不能只数自己写了几行代码。

## 是让模型填表，还是让模型写一小段程序

要比较三个时间段的车次，一种办法是让模型分别调用查询工具。每次填好出发地、目的地和时间，工具负责检查参数再查询。

另一种办法是让模型写一小段循环，一次组织这几个查询。smolagents 的代码行动提供了这种方向，也保留了其他行动方式。

前一种做法便于把规则藏在工具里面：查询日期必须正确，不接受下单请求。后一种做法更灵活，但运行那段代码的地方必须限制能访问的文件、网络和账号；代码出错时还要能找出错在哪。

因此，固定的操作适合做成明确工具，临时的数据组合可以考虑受限制的代码。能否省时间，要连同查询失败、代码调试和最后检查一起算，不能只看模型少说了几轮话。

## “保存过”之后，下一次能不能用上

用户说喜欢安静住处。助手把这句话写进文件，隔天却继续推荐热闹街区。这时，磁盘上确实有记录，但下一次选择并没有用上它。

LangGraph 把执行检查点和长期存储分开：前者帮助接着上次进度做，后者提供保存跨任务信息的地方，具体存什么、何时读仍由应用安排。OpenAI Agents SDK 的会话机制主要保留历史，也不会自动把每句话整理成长期偏好。

Codex、Gemini CLI、Qwen Code 的后台记忆路径进一步处理历史里哪些内容值得提取、何时整理、怎样进入后续输入。OpenCode 对持续指令的来源变化另有记录，不能把它与自动提取历史当成一回事。

还有些差异藏在读写顺序里。CrewAI 在相应召回路径上等待排队写入完成；Letta Code 的公开本地实现按已提交的记忆文件编译模型输入。它们分别回答“刚写的东西能读到吗”和“模型用的是哪份文件”。

所以，如果要求助手下次一定记住偏好，就要从保存一路看到下一次请求：写到哪里，谁去读，读到的内容有没有交给模型。找到一个保存接口，只做完了其中一步。

## 多请一个助手，谁来把结果拼好

交通和住宿可以分头查。但交通助手找到了便宜的晚班车，住宿助手安排了下午入住，两份结果单独看都正常，放在一起却不合适。

AutoGen、AgentScope、CAMEL、ADK 提供不同的团队组织方式。选择时先问：几个成员是各查各的资料，还是会一起改同一份行程？后者更容易出现覆盖和冲突。

再问：成员查完后，谁检查它交回了什么？有的团队里，小助手因次数用完而停下，主助手仍会收到一条普通工具回复。如果只看有没有报错，就可能把没查完当成查完。Hermes 的子任务可以另有一份运行预算，也不能把父任务的上限当作整个团队的上限。

如果一个人先拟方案、另一个人再修改就够了，串行交接可能已经合适。只有节省下来的等待时间，超过分派、沟通和核对的时间，多 Agent 才值得加入。

## 程序重启后，怎样避免再做一次

假设用户后来允许把确认后的行程加到日历。日历里已经有了那条安排，助手却在保存结果之前退出。再次启动时，它该重新创建，还是先查一查？

LangGraph 的检查点、PydanticAI 可选的持久执行集成、Mastra 的不同运行方式，以及 OpenCode 的恢复机制，保存和重新执行的范围并不一样。记录了程序做到哪里，不等于知道日历服务已经做了什么。Cline SDK 对本地文件的回滚，也不能撤回远端已经创建的日程。

这需要两边配合：助手保留这次添加操作的标记，日历服务能据此找到已有日程，或识别重复请求。程序决定从哪里继续，服务确认上次动作是否已经发生。

## 带着自己的要求去选

| 你希望助手做到什么 | 选择时该问什么 |
| --- | --- |
| 查不到合适车次时换一种办法 | 模型能否读到结果，再决定下一步？ |
| 绝不擅自订票订房 | 真正执行时，由谁拦住未获准动作？ |
| 下次还记得住宿偏好 | 保存后，下一轮怎样读到它？ |
| 重启后不重复添加日程 | 怎样找回上次操作和服务结果？ |
| 两个助手一起做一份行程 | 谁核对日期、费用和最终安排？ |

这些问题比“哪个项目最强”更容易回答，也更接近自己的工作。一个项目可以帮你做其中几项，其余部分仍要有人负责。

选完以后，还要面对下一天：关掉程序再打开，换一个人维护，助手是否仍然知道已经查到什么、还有什么没做好？
