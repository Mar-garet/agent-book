# 第十章：把项目放在同一张问题地图上

团队准备把报表助手留下来。有人想采用现成的编程助手，有人想自己装配工具循环，还有人希望把审批、测试与验收固定成一条流程。三个人都想交付 R42，却把不同的责任留给了开发者。

选型最容易走错的一步，是先问“谁的功能最多”。一个项目提供记忆接口，另一个项目替用户维护记忆；一个项目能保存执行进度，另一个项目能确认远端动作是否已经发生。这些能力名字相似，需要补的工作却不同。

我们先把任务放回桌上：调查生产运行 `run-807`，核对 10 月 15–16 日的数据，生产只读，修复在测试环境验证。选择任何项目，都要说明这些要求由谁守住。

## 先分清要买到哪一层责任

直接面向使用者的运行系统，已经安排了一部分工具、交互、权限和会话管理。Codex、Gemini CLI、OpenCode、Goose 等属于这种讨论范围；接入后，团队首先要理解它们的默认行为和扩展边界。

Agent 框架让开发者定义模型、工具和应用状态。OpenAI Agents、ADK、PydanticAI、AutoGen 等给出不同的装配方式，团队仍须决定业务授权、长期事实和交付标准。LangGraph 进一步把有状态执行组织为图，适合明确表达阶段与恢复位置。Deep Agents 又在图与 Agent 构建机制上组合文件、上下文和委派等长任务能力。

MCP 处在另一层：它约定宿主怎样发现和调用服务。报表服务采用 MCP，并没有替宿主决定谁批准重跑、怎样保留大结果、什么时候重试。

这些层次可以共同出现。需要比较的是替换一层之后，哪些责任由新组件接手，哪些责任仍留在应用里。

## 开放探索，还是固定转移

调查 E42 时，我们很难预先写死每一步：先看日志还是配置，取决于刚刚发现的线索。这适合交给模型在允许的工具之间选择。Pi 的核心循环提供一个较小的起点；LangChain 的 Agent 构建机制、OpenAI Agents 等也可以组织模型与工具往返。工具、上下文和停止规则仍需按应用需求配置。

另一些转移却不该临场猜测：超出当前授权的动作不能派发，没有读到完整产物就不能交付。这类要求适合由程序固定。LangGraph 可以把诊断、等待授权和验收组织为明确节点；Agent Framework 的工作流也有自己的步骤、状态与检查点。开发者付出的代价，是维护状态定义与每条失败路径。

Aider 展示了另一种有用的收束方式：先形成修改方案，再交给编辑阶段执行，并通过 lint 或测试结果继续修正。这里的分工围绕一项明确产物展开。增加角色本身没有产生价值；缩小每个阶段的任务，才让错误更容易被发现。

对 R42，一个自然的组合是：程序守住环境、授权和验收门槛，模型在诊断阶段自由调查。选择框架前，先试着画出这条责任分界。

## 方便的默认机制，意味着接受哪些约定

第一版助手只查询两种资料时，开发者可能愿意自己装配工具与状态。任务开始积累文件、历史和子任务后，Deep Agents 的组合机制、OpenClaw 的工作区组织、Hermes 的持续使用机制等，就提供了不同程度的现成安排。

但“有这个能力”不能代替配置判断。Deep Agents 的存储后端、memory 与 skills 配置会改变实际行为；Goose 的记忆可以来自可选扩展；Agno 的记忆管理也有启用条件。把可选能力当成默认能力，会让第一轮演示看起来成立，换一个环境却无法复现。

默认机制越多，应用需要逐项接线的工作可能越少，也越需要理解这些机制怎样共同更新状态。默认机制越少，应用更容易看清自己接入了什么，也必须主动补齐遗漏的责任。两种路线都不能仅凭代码行数判断成本。

## 模型填写参数，还是编写行动

假设另一项报表任务需要核对连续七天。助手可以七次调用日期查询，也可以写一段循环来组合查询和校验。

结构化工具让模型填写参数，把对象范围、权限和业务约定留在工具内部。smolagents 的代码行动则允许模型用程序表达组合，循环、分支与临时数据处理可以直接写出来。它也提供其他行动方式，不能用一种执行模式概括整个项目。

组合更灵活，执行环境就需要承担更多责任：代码能访问什么、失败后如何定位、外部动作能否撤回。稳定的报表操作适合封装成带校验的工具；探索性的只读组合可以使用受约束代码。比较成本时，要一起计算模型往返、执行失败和结果验证。

## 状态存下来之后，谁让它再次生效

给 R42 选系统，不能只问是否支持“持久化”。至少有三件不同的事：恢复昨天的执行位置，记住项目规则，以及知道远端已经接受哪次动作。

LangGraph 将执行检查点与跨线程存储区分开，长期知识的写入和读取仍由应用安排。OpenAI Agents 的会话机制保存历史，它不会自动把所有历史变成有效的业务事实。OpenClaw、Hermes 等长期使用系统，则把文件、精选内容、历史查找与输入组织放进更完整的使用路径。

Codex、Gemini CLI、Qwen Code 展示了后台记忆更新中的另一层工作：提取何时触发、任务如何协调、候选内容如何进入下一轮。OpenCode 对持续指令来源的内容版本和更新事件另有管理，让来源变化能够进入后续输入。CrewAI 的统一记忆在召回前等待已排队的写入，Letta Code 的本地记忆编译路径则关注文件提交与输入更新。这些差别说明，选定存储介质之后，真正的设计才刚刚开始。

如果团队要求“新规则已经接受，下一次行动必须读到”，就应检查从写入到输入的完整链路。只找到一个保存接口，还没有回答这个问题。

## 更多 Agent，交付责任会不会消失

日志调查和字段核对可以并行，但它们最终要回到同一份解释。AutoGen 的团队调度、AgentScope 的团队执行、CAMEL 的工作分配、ADK 的层级与协作机制，都提供不同的组织方式。比较时，先确认参与者是在处理独立材料，还是正在改变同一份共享状态。

随后追问三件事：协调者拿到什么结果，成员停止意味着什么，原任务还剩多少预算。Hermes 子任务可以拥有独立预算；OpenCode 的持久任务需要处理完成事件与恢复；某些团队接口返回的成功状态还可能包住成员达到迭代上限的结果。协调者必须解释成员产物，不能把“调用返回”直接变成“业务完成”。

若只是先拟方案再编辑，串行交接往往已经足够。只有当并行节省的等待超过协调、共享和核查的成本，更多 Agent 才值得加入。

## 恢复执行，能保证什么

测试平台可能已经创建任务，连接却在响应返回前中断。此时恢复程序必须判断：重新发送，还是查询已有动作？

LangGraph 的检查点、PydanticAI 可选的持久执行集成、Mastra 不同的持久运行路径、OpenCode 的执行认领与恢复，各自保存和重放的单位并不相同。快照记录了本地进度，不能单独证明外部系统没有执行。Cline SDK 的本地修改回滚，也不能撤销一项远端业务写入。

因此，报表平台应接受稳定的动作编号，并允许应用按编号查询结果。运行系统决定从哪里继续，业务服务决定同一动作是否再次生效，两者需要一起设计。

## 把选择落到可以验收的条件上

| 眼前的约束 | 应先核查的机制 | 团队仍须承担的工作 |
| --- | --- | --- |
| 调查路线经常变化 | 模型与工具循环、结果反馈 | 限定对象、工具和停止条件 |
| 审批与验收顺序固定 | 状态转移、暂停与恢复 | 定义阶段以及失败转移 |
| 新规则必须及时生效 | 写入、刷新、召回与输入链 | 定义适用范围和生效时间 |
| 外部动作不能重复 | 稳定动作编号、状态查询 | 与业务服务约定幂等性 |
| 多个成员共同交付 | 交接产物、成员状态与预算 | 由协调者检查最终证据 |

这张表没有给项目排总名次。R42 需要的分工已经清楚：运行系统持有进度，模型选择调查步骤，业务工具限定操作范围，验收器独立读取产物。项目可以承载一层或几层，但每项责任都要有明确的主人。

选型讨论到这里，下一步才有意义：如果明天换一个工程师接班，今天要留下什么，他才能判断助手做到哪里、还可以做什么？
