# 第十章：把项目放在同一张问题地图上

已经看过工具、MCP、记忆和协作，再打开一个项目的功能列表，读法应该有所变化：每个功能名称背后，都对应某项需要承担的责任。

本章采用本地固定快照比较。源码研究覆盖执行、上下文、记忆、MCP 与协作的局部调用链；运行观察进一步检查恢复、错误处理、委派预算与摘要输入。完整任务效果与跨项目性能仍未评测，详细范围见 [研究记录](../references/studies/README.md) 与 [实验目录](../experiments/README.md)。

## 比较前，先找到项目所在的层次

Pi、Codex 这样的运行系统提供直接工作的入口。LangGraph 提供组织有状态执行的基础。LangChain 连接模型、工具和应用构建机制。Deep Agents 在这些基础上提供更多长任务默认机制。MCP 则约定系统之间如何交换能力与调用请求。

它们可以出现在同一套系统中。比较时应说明，正在评价的是现成体验、应用开发工作量，还是某一层机制的可控程度。[层次说明](../references/evidence.md#l02-langchain-生态层次)

例如，不能只因一个基础框架没有提供某种终端交互，就推断其执行结构无法支持这类交互；也不能因为某种能力理论上可以扩展，就省略实现它需要的工作。

## 比较一：Pi 与 Deep Agents，把多少选择放在默认机制里

**已核对的事实**。Pi 的 README 将自身描述为可扩展的极简运行系统，并说明子 Agent、计划模式等做法可以通过扩展形成。Deep Agents 的材料则提供子 Agent、文件系统、上下文管理、Skills 等默认机制。[P01](../references/evidence.md#p01-pi-的默认取向) · [L02](../references/evidence.md#l02-langchain-生态层次)

**设计推断**。Pi 的取向让使用者更早面对“自己需要怎样工作”的问题；Deep Agents 的取向让使用者先采用一套已有工作方法，再决定替换哪些部分。两种方式可能把定制工作放在不同时间发生。

**还需要验证**。在短任务、复杂长任务和高度定制任务中，配置成本、额外步骤、完成质量分别怎样变化？某个扩展安装之后，比较对象已经发生变化，需要重新记录配置。

**第二轮补充**。Deep Agents 的当前通用构造栈不应直接概括为“默认包含所有规划、Skills 和持久记忆”。相关参数、模型 profile、后端与应用装配会改变实际能力。Pi 与 Deep Agents 还在同文件并发修改上采用不同协调方式：前者的文件工具排队，后者的文件中间层拒绝同批后续冲突调用。[执行与默认装配研究](../references/studies/pi-deepagents-execution.md)

“极简”不能直接推导性能更高；“默认机制更多”也不能直接推导任务更可靠。

## 比较二：LangChain、LangGraph 与 Deep Agents，开发者自己决定多少流程

**已核对的事实**。Deep Agents 的材料明确描述三层关系：图执行基础、较轻的 Agent 构建机制、带更多默认能力的运行系统。LangGraph 也可以在不使用 LangChain 的情况下单独使用。[L01](../references/evidence.md#l01-langgraph-的执行状态) · [L02](../references/evidence.md#l02-langchain-生态层次)

**设计推断**。如果主要困难是一个特殊的状态转移过程，直接安排执行结构可能更贴近问题；如果主要困难是为通用长任务补齐文件、委派和上下文机制，采用已有默认机制可能减少前期拼装工作。

**还需要验证**。一个真实需求变化后，需要改动多少地方？状态、工具错误和人工介入能否按业务要求表达？应用自定义逻辑是否越来越多地绕开默认机制？

这里评价的是应用设计与维护成本。没有实验，不能据此宣称某层框架在任务效果上全面优于其他层。

## 比较三：OpenClaw、Hermes 与 LangGraph，记忆责任放在哪里

**已核对的事实**。OpenClaw 描述了工作区文件、启动加载与日记检索。Hermes 描述了有界长期信息、会话开始快照和历史搜索。LangGraph 的检查点与长期存储提供不同的持久化职责。[M01](../references/evidence.md#m01-openclaw-的文件记忆) · [M02](../references/evidence.md#m02-hermes-的记忆与历史) · [L01](../references/evidence.md#l01-langgraph-的执行状态)

**设计推断**。前两者提供较具体的使用约定，使用者需要理解它们何时写入与生效；底层存储机制留下更多业务策略，由应用决定写什么、怎样更新、何时取回。

**还需要验证**。新规则何时进入实际输入？旧规则怎样停用？两个用户的信息是否隔离？记忆写入失败时，系统是否仍声称已经保存？

**第二轮补充**。Hermes 的普通写入与系统提示刷新分开；正常在线压缩提交又提供了重新加载边界，保留前缀的后台路径有不同处理。OpenClaw 的自动加载还要检查会话范围、来源和预算。Markdown 与数据库索引可以同时存在，不能按存储格式推断全部记忆行为。[更新边界专题](15-memory-update-boundaries.md)

存储格式可以影响可检查性与运维方式，但不能单独决定记忆质量。

## 比较四：结构化工具调用与代码行动，组合发生在哪里

**已核对的事实**。smolagents 把代码行动作为重要方向：模型用代码表达动作，再交给执行环境。它讨论的是动作如何表达，而不只是一种编程用途。[T01](../references/evidence.md#t01-smolagents-的代码行动)

**设计推断**。将多个调用组合成代码，可能减少模型往返，也会把循环、异常和中间变量带入代码执行环境。单次结构化工具调用的边界较明确，但复杂组合可能需要更多轮次。

**还需要验证**。相同任务下，减少了多少模型请求，增加了多少执行错误与调试工作？隔离与审计是否仍能覆盖组合动作？

## 比较五：Codex 与其他运行系统，执行边界怎样进入行动链

本轮已核对 Codex 的工具审批与沙箱相关源码入口，也读到 Pi 对进程权限与扩展执行方式的说明。这说明我们应该沿执行路径检查边界，而不只读取提示词中的约束。[C01](../references/evidence.md#c01-codex-的工具执行边界) · [P02](../references/evidence.md#p02-pi-的会话与压缩)

目前信息不足以给出总体安全性排名。公平比较需要指定操作系统、策略、工具类型、扩展和攻击场景，观察实际允许与拒绝了哪些动作。

**第二轮补充**。命令用户会话授权与 MCP 工具会话授权具有不同匹配范围；命令启动阶段与后续输出收集阶段的拒绝，也不进入完全相同的重试流程。比较应当沿真实路径确定审批对象、权限变化和结果语义。[执行链研究](../references/studies/codex-tool-execution.md) · [动作边界专题](12-action-boundaries.md)

## 比较六：Goose 与 Cline SDK，相同协议之上怎样安排工具

**已核对的事实**。Goose 的常规扩展路径与 Cline SDK 都要筛选和转换服务工具；Goose 的可选 Code Mode 还提供逐步发现和代码调用。目录变化、模型工具重建与请求更新具有不同边界。Cline SDK 的结论不自动覆盖同仓库的 VSCode 产品。[MCP 宿主研究](../references/studies/goose-cline-mcp.md)

**设计推断**。直接提供完整工具说明，可能减少发现步骤；逐步发现，可能节省最初的输入空间。调用后的大结果还需单独安排读取与保留，无法只靠减少工具定义解决。

**还需要验证**。在工具目录相同、模型和任务相同的条件下，分别消耗多少输入、往返与等待？目录更新与临时输出失效时，模型会怎样继续？这些需要实际请求与服务事件，不能从功能列表推算。[宿主差异专题](16-mcp-host-differences.md)

## 把“功能对比”变成可以研究的问题

后面的章节把这些问题继续拆细。相同的错误，可以被转换成模型看到的消息，也可以触发节点重试；相同的多 Agent 结构，可以共享一次运行的轮数，也可以启动独立计数的子运行。配置名称相似，约束的位置仍可能不同。比较时应当沿 [工具结果](17-tool-results-and-retries.md)、[委派](19-delegation-and-handoffs.md) 与 [预算](21-execution-budgets.md) 的实际流程说明差异。

| 维度 | 应当追问 | 可核查的记录 |
| --- | --- | --- |
| 行动循环 | 谁决定下一步，何时结束？ | 运行入口、轨迹、停止状态 |
| 工具接入 | 能力怎样呈现，错误怎样回来？ | 描述、执行链、错误样例 |
| MCP | 宿主怎样筛选与执行工具？ | 配置、发现流程、调用记录 |
| 上下文 | 模型这一轮实际看到了什么？ | 请求输入、摘要、外置记录 |
| 记忆 | 何时写入、更新、生效与失效？ | 存储内容、读取路径、跨会话实验 |
| 协作 | 谁委派，谁汇总，谁验收？ | 子任务输入、结果与控制流 |
| 可靠性 | 中断后怎样确认外部效果？ | 检查点、动作标识、恢复实验 |
| 成本与质量 | 在什么任务和预算下成立？ | 可重现任务集与多次记录 |
