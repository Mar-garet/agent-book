# 第十章：把项目放在同一张问题地图上

团队准备把报表助手留下来。有人建议用 Pi：工具少，执行过程容易看清。有人看中了 Deep Agents 的文件与上下文机制。还有人提出，既然每次都得确认环境、等待任务、检查结果，干脆用 LangGraph 把这些步骤安排好。

三个人讨论的是同一份 R42 报表，却在回答不同的问题：直接采用什么工作方式，要自己装配多少能力，哪些转移必须由程序固定。把项目名称摆成一排，还没有开始比较。

本章只比较本地固定快照中已经核对的机制。源码与运行范围集中保存在[研究记录](../references/studies/README.md)和[实验目录](../experiments/README.md)；下面的方案选择是针对报表案例的设计判断，不是跨项目性能排名。

## 比较前，先找到项目所在的层次

此时，我们已经给任务加了三条要求：调查 `run-807`，生产只读，修复方案只能在测试环境验证。接下来要选的系统，应当让这些要求有明确位置。

Pi、Codex 这样的运行系统提供直接工作的入口。LangGraph 提供组织有状态执行的基础。LangChain 连接模型、工具和应用构建机制。Deep Agents 在这些基础上提供更多长任务默认机制。MCP 则约定系统之间如何交换能力与调用请求。它们可以出现在同一套应用中。[层次说明](../references/evidence.md#l02-langchain-生态层次)

因此，比较时要先说清谁来补齐工作。一个框架把流程留给开发者，开发者就要维护状态与转移；一个运行系统已经安排好工具和交互，使用者就需要理解并调整它的默认行为。接口调用只有一行，背后的设计工作未必只有一行。

## 比较一：Pi 与 Deep Agents，把多少选择放在默认机制里

假设第一版助手只需要查询日志、读取配置，再提交一份报告。团队愿意自己控制工具与会话，Pi 的可扩展核心提供了一个可以逐步装配的起点。它将计划、子 Agent 等工作方式留给扩展，取舍是应用需要明确补上什么。[Pi 的项目说明与范围](../references/evidence.md#p01-pi-的默认取向)

如果任务已经需要文件外置、历史整理与子任务，采用更多现成机制可以减少逐项接线。Deep Agents 的构造栈提供这类能力，但具体装配仍受参数、模型 profile 和后端影响。例如，memory 与 skills 的配置不能直接从“长任务框架”这个名称推断。[默认装配研究](../references/studies/pi-deepagents-execution.md)

选择于是变得具体：愿意维护一套小而明确的处理链，可以从较少默认机制开始；希望采用现成的长任务组织方式，就先核查默认栈是否符合自己的状态和权限要求。前者的代价是装配，后者的代价是理解、调整与持续跟进默认行为。工具少或机制多，都还不能推出任务更快、更可靠。

两者对同文件修改的处理就展示了这种差别。Pi 的编程文件工具让同一路径排队；Deep Agents 的文件中间层拒绝同批后续冲突调用。排队把协调放在工具内部，拒绝则让后续决策重新安排。团队如果不能接受并发覆盖，需要检查这一个位置，而不是为整个项目贴上“支持并发”的标签。[执行与文件修改研究](../references/studies/pi-deepagents-execution.md)

## 比较二：LangChain、LangGraph 与 Deep Agents，开发者自己决定多少流程

现在，值班工程师增加了一条硬要求：没有确认目标环境，就不能修改；没有读到最终产物，就不能交付。

这样的阶段顺序比较稳定，适合由程序表达。LangGraph 提供图执行基础，应用可以把“确认环境—诊断—获准验证—验收”设成明确转移，把开放探索留在诊断节点内部。代价是开发者要维护状态定义、失败转移和恢复语义。[执行状态与范围](../references/evidence.md#l01-langgraph-的执行状态)

若主要工作是一轮轮选择工具，LangChain 的 Agent 构建机制可以承担行动循环；若还希望采用文件、子 Agent 和上下文管理等长任务组织方式，Deep Agents 再在这层基础上装配默认机制。固定文档给出的正是这三层关系；LangGraph 也可以单独使用。[层次依据](../references/evidence.md#l02-langchain-生态层次)

对 R42，合理的设计不必让模型决定所有转移。应用可以固定生产写入限制和验收门槛，让模型决定先查哪一条证据。选择框架时，先看这种分工能否自然表达，再看需要多少自定义代码。

## 比较三：OpenClaw、Hermes 与 LangGraph，记忆责任放在哪里

值班工程师不想每天重说一次时区和项目约定。这时，“有持久存储”还不够：新任务怎样得到当前有效规则，才是要选的工作方式。

OpenClaw 以工作区文件承载用户资料、长期事实和日记，并安排加载与检索路径；Hermes 将精选信息、提示快照和历史会话搜索放在持续使用的体验中；LangGraph 区分执行检查点与跨线程长期存储，保存什么、什么时候读，更多由应用定义。[OpenClaw](../references/evidence.md#m01-openclaw-的文件记忆) · [Hermes](../references/evidence.md#m02-hermes-的记忆与历史) · [LangGraph](../references/evidence.md#l01-langgraph-的执行状态)

个人助手只有少量经常使用的约定时，可以先考虑容易查看、修改的精选区域。团队需要按项目隔离、表达生效时间并处理多人更新时，应把这些规则放进可核查的业务结构。长任务恢复还需要检查点记录执行进度；一份长期偏好文件无法告诉程序昨天已经创建了哪张审查单。

这是按用途选责任，不是按 Markdown 或数据库选阵营。具体写入、刷新、检索与更新，将在[记忆系统](15-memory-update-boundaries.md)中展开。

## 比较四：结构化工具调用与代码行动，组合发生在哪里

助手要核对连续七天的报表。可以逐日提出七次查询，也可以生成一段循环，把查询和汇总组织在一次代码执行中。smolagents 的代码行动提供了后一种方向，同时也有其他调用方式。[项目材料](../references/evidence.md#t01-smolagents-的代码行动)

如果团队已经有带范围校验的报表查询接口，让模型填写环境与日期区间，能把更多业务约定留在工具内部。若需要临时组合大量独立读取，代码表达更有弹性，但执行环境、调试、错误定位和权限隔离也进入维护范围。

两者可以一起使用：稳定的业务操作提供明确接口，探索性组合使用受约束代码。能否减少总成本，需要把模型往返、代码失败和验证过程一起测量；仅数模型调用次数，容易漏掉工作被移到了哪里。

## 比较五：Codex 与其他运行系统，执行边界怎样进入行动链

团队接着问：如果模型仍然提出生产修改，谁能在真正执行前拦住？

Codex 的命令路径把参数解释、命令策略、审批和实际执行限制放在不同步骤。Pi 也有调用前检查与工具执行边界，但核心、编程工具和宿主扩展各自承担不同部分。比较需要走到实际动作，确认哪个检查会拒绝这次请求。[Codex 执行研究](../references/studies/codex-tool-execution.md) · [Pi 执行研究](../references/studies/pi-deepagents-execution.md)

对于 R42，先写出一条可检查的要求：持有生产读取凭证的诊断工具，不能因为模型在参数里声称“已批准”就获得写入能力。应用在选择运行系统之后，仍要配置对应工具和服务权限。某套系统是否更安全，需要固定平台、策略和具体场景另行验证。

授权还能否复用，也要看匹配单位。Codex 的命令会话授权与 MCP 工具授权采用不同范围；将它们都称为“记住批准”会掩盖差别。这个问题留到[可靠执行](12-action-boundaries.md)沿调用链拆开。

## 比较六：Goose 与 Cline SDK，相同协议之上怎样安排工具

团队决定共用日志服务和报表服务的 MCP 接口，但还要选择宿主怎样把它们交给模型。Goose 常规路径与 Cline SDK 都会筛选、转换工具；Goose 的可选 Code Mode 还安排逐步发现与代码调用。[宿主研究](../references/studies/goose-cline-mcp.md)

工具集合小而稳定时，直接给出完整说明容易追踪一次选择。连接的能力越来越多时，按任务筛选或逐步发现值得考虑，但模型也要多走寻找入口、读取说明的步骤。这里只给出条件选择，未测量两条路径的延迟或成功率。

调用之后，宿主怎样保留大结果、处理错误和更新目录，会继续影响排障。选择时可以沿一份日志追问：服务已经返回，模型实际看到了哪部分，还能不能找回尾部？[工具系统](16-mcp-host-differences.md)将沿这个问题继续。

## 把“功能对比”变成可以研究的问题

讨论结束后，团队先确定了一套分工：运行程序持有任务与权限状态，模型选择调查步骤，业务工具固定对象范围，验收组件独立读取产物。具体项目可以承载其中一层或几层，替换它时也要说明哪些责任一并改变。

这比选出一个“功能最多”的项目更接近工作目标。接入后的第一个检查，不是看助手说得是否流畅，而是看它能否始终围绕 `R42 / run-807 / 生产只读、测试验证` 这份任务工作。

需要核对本书覆盖了哪些项目，可查[32 个项目的研究地图](../references/project-map.md)；固定版本在[源码目录](../docs/source-catalog.md)。接下来，我们把选型讨论放回值班现场：当助手明天还要继续工作，今天需要留下什么？
