# 第五章：上下文——Agent 此刻究竟看见了什么？

助手已经读过几张车次表和很长的酒店页面。你接着问：“这家住处合适吗？”

模型下一轮看到的，可能有房间照片的说明、早餐介绍和几十条评价，却没有最初那句“总预算 1500 元，不订票、不订房”。也可能记得出发，忘了周日还要回上海。

问题不一定是资料没保存。有些内容仍在聊天记录里，只是没有被放进这一次请求。

## 上下文，就是这一次给模型看的内容

模型每次回答，都要收到一份输入。本轮输入里实际包含的指令、聊天、工具说明、网页片段和查询结果，合起来叫作“上下文”。

它不会自动读完应用保存的所有文件，也不会因为用户曾经说过，就永久拥有那句话。运行程序要负责选出内容，再送给模型。

所以，助手突然开始推荐超预算酒店时，应先看它当时收到什么。1500 元是否还在？住宿价格是不是那晚的？网页有没有说明费用还要另加？这样才能区分是材料缺失，还是模型拿到正确材料后仍判断错误。

## 哪些要一直留着，哪些可以先放一边

输入能容纳的内容有限，处理长输入也需要时间和费用。酒店页面再长，也不应该挤掉这次旅行最重要的几项要求。

可以先留下这样的工作记录：

```text
要求：上海到杭州，周末两天，住一晚，总预算1500元。
限制：先给草稿，不订票、不订房，日历另问。
已查到：一班合适的去程；两家可比较的住处。
还没确认：周日返程、各项费用合计。
需要细看：其中一家酒店的周六房价与取消说明。
```

这几行让下一轮知道该做什么。详细车次表和酒店原文可以另存，等比较时再读取相关部分。这样少占输入空间，却增加了一次取回资料的工作，也要求保存位置仍然可读。

## 摘要会省字，也会省掉条件

“用户要安排杭州旅行”很短，却没说预算、不下单和返程要求。“已讨论酒店”也没有告诉接手的模型，房间是否可用、价格是否核实。

好的摘要要保留会改变下一步的内容。暂时放弃某家酒店，可以只留下原因；用户不允许付款，则应持续清楚地表达。

Pi 把完整会话记录与当前分支要发送的消息分开。LlamaIndex 的新 Memory 组件则会按预算组织近期消息和可选的长期内容。做法不同，都说明“过去记录了什么”和“本次发给模型什么”需要分别管理。

保存原文给了补查的机会，却没有自动完成补查。摘要中还要说明，哪家酒店的哪段内容值得再读。

## 找到相似资料，不代表适合这次使用

助手可能找到别人去杭州的旧攻略。路线很像，酒店很便宜，却是淡季价格；也可能找到你上次的旅行记录，但那次没有 1500 元限制。

先从大量资料中找相关内容，再把选中的内容交给模型，通常叫作 RAG，即检索增强生成。它能帮助找资料，却不能单独保证日期、对象和条件都匹配。

查询结果应带着网页来源、查询时间和适用日期。模型用旧攻略推荐路线可以，用旧房价保证这周末住得到，就超出了材料能够说明的范围。

## 网页太长，可以少读，但要知道少读了什么

Deep Agents、CrewAI 等系统有条件地把大工具结果另存，再提供预览或读取方式。应用因此不必把整页都放进每次请求。

代价是模型可能只看预览，没有读到正文里的重要条件。临时缓存还可能过期。“页面前半段没写额外收费”，不能推出整页都没有。

本书对 Pi 一个真实序列化函数做过小型检查：将唯一标记放在长工具结果末尾时，标记没有进入给摘要器的材料。检查没有调用模型，只说明内容在到达摘要器前已经被裁掉；更换摘要模型无法从这份材料找回它。

对旅行助手，可以先提取房价、对应日期和费用说明，再保留原文位置。若资料不足，就继续读，而不是把没读到的条件当作不存在。

## 怎样看出整理是否有用

输入变短只是一个结果。还要看 1500 元、不下单、周日返程有没有保留，房价能不能回到原页面核对，助手是否真的按这些条件写行程。

如果要求没进输入，先改内容选择；如果要求在，模型仍忽略，再检查它的判断与发出草稿前的核对。两种失败不该用同一种办法处理。

现在，助手每轮都有一份较清楚的工作材料。可是换个会话以后，它还能想起你喜欢安静的住处吗？这就要进入记忆的问题。
