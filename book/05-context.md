# 第五章：上下文——Agent 此刻究竟看见了什么？

R42 的调查继续推进。日志 artifact:log-17 的第 840–875 行出现错误 E42，提示字段映射问题；助手还要把它与配置版本 v6、源分区核对。与此同时，工具已经返回大量无关日志。

下一轮请求时，模型还看得到“生产只读，测试验证”这条任务边界吗？它还分得清 E42 是线索，还是已经确认的根因吗？

这个问题经常比“系统一共存了多少记录”更重要。

## 存在系统里，不代表进入了本轮输入

**上下文**是本轮模型请求实际获得的信息。它可以包括任务指令、用户消息、工具描述、历史摘要、检索片段和工具结果。

运行系统决定如何组装这些内容。模型没有自动阅读所有磁盘文件、历史会话和数据库的能力；相关信息需要被加载，或者通过工具取得。

因此，分析一次错误时，可以先重建模型当时的输入：关键约束是否存在，是否被截断，是否夹在大量无关结果里，来源是否清晰。

## 上下文有一个需要管理的预算

模型请求能够容纳的信息有限，处理信息也需要时间与成本。把所有内容都塞进输入，会挤占其他信息的空间。

系统通常要做三种选择：保留什么，压缩什么，暂时放到外部什么地方。选择的依据应当与任务下一步有关。

例如，完整日志可以保留在外部，本轮只带入 E42、run-807、业务日期，以及 artifact:log-17 的第 840–875 行位置。这样既给核对配置留下空间，也保留回查原文的路；代价是助手需要细节时还要多读一次。

## 压缩是一种有损的决策

把一百条历史消息变成摘要时，某些细节会被省略。摘要如果只写“允许修改配置”，就可能丢失“仅测试环境”和“今天临时允许”两个重要条件。

一份对行动有用的摘要需要保留目标、约束、已验证事实、尚未确定的判断、关键决定与下一步。原始材料的位置也应尽量保留，让系统有机会重新核查。

Pi 的材料说明，会话记录可以形成分支，模型使用当前活动分支；压缩为后续请求加入摘要，而原始记录仍保留在会话树里。这使“用于当前推理的输入”和“可以回查的历史”具有不同形状。[参考 P02](../references/evidence.md#p02-pi-的会话与压缩)

保留原始历史有助于追溯，但系统还需要知道什么时候回查、怎样找到对应片段。存档本身没有完成这一步。

[上下文装配专题](13-context-and-defaults.md) 会沿 Pi 的原始会话树、当前分支和最终请求，追踪这些选择实际发生在哪里。

## 检索带回信息，也带回适用范围问题

检索可以从大量资料中选出相关内容。相关性只是一个条件。

一份去年写的部署说明，可能与今天的问题高度相似，却已经失效。一段针对另一个客户的解决方案，可能技术上适用，却不属于当前授权范围。

因此，检索结果最好同时携带来源、时间、对象和适用条件。模型或程序在采用结果前，需要判断它是否与当前任务匹配。

**RAG**，检索增强生成，是先检索外部资料，再把选中的内容提供给模型的做法。它是一条信息获取路径。资料是否更新、查询是否正确、片段是否完整，都需要在这条路径上处理。

## 上下文的顺序和来源也有意义

同一段话来自用户、系统配置或外部网页，具有不同的作用。运行系统需要保留这些边界，避免把网页里的内容变成对整个任务的指令。

工具结果也需要控制体积。一条错误返回十万行日志时，直接加入下一轮输入可能影响其他信息。Deep Agents 将长对话摘要与工具输出外置列为上下文管理能力，可以作为进一步研究的案例。[参考 L02](../references/evidence.md#l02-langchain-生态层次)

这带来一个新的问题：外置之后，模型是否还知道重要细节在哪？[MCP 宿主专题](16-mcp-host-differences.md) 会追踪临时结果缓存的读取与失效；[上下文压缩专题](18-context-compaction.md) 则用真实序列化函数观察，哪些信息在摘要模型读取之前已经被裁掉。

## 怎样观察上下文管理是否有效

不要只测输入长度是否减少。还要测关键约束的保留、事实误记、原文回查成功率，以及最终任务是否完成。

一种验证办法是先放入“生产只读，测试验证”，再插入大量无关日志，比较压缩前后这条限制和 E42 的证据位置是否仍可找到。涉及模型行为的比较还应重复运行，保留实际输入与结果。

R42 已经有了一份较小、可回查的当前工作材料。可是一旦新会话开始，这些材料是否还会被找回来？上下文解释了“现在看见什么”，记忆还要解释“下次为什么能想起”。
