# 第八章：Skills 与多 Agent——经验和分工怎样进入系统？

报表排查已经做过几十次。团队希望 Agent 复用其中可靠的做法，也希望复杂任务可以交给不同助手处理。

这里有两个方向：把经验整理为可加载的工作方法，以及把任务组织为多个执行者之间的协作。它们可以结合，却承担不同责任。

## Skills 怎样把经验变得可复用

在 Pi 等项目里，Skill 可以包含按需加载的说明与辅助文件。系统先提供简要描述，任务需要时再加载具体内容。[参考 P02](../references/evidence.md#p02-pi-的会话与压缩)

一份排查 Skill 可以写明：先确认环境与日期，怎样选择日志，遇到哪些异常要停止自动修改，最后用什么方法验收。它还可以带示例、脚本与检查材料。

这使经验有了明确位置，也减少了每轮重复提供全部细节的需要。但说明能否正确触发、是否过时、脚本是否适用于当前环境，仍要验证。

如果一项约束必须在任何情况下强制执行，应当把它落实到权限或工具检查中。工作说明可以帮助模型做出合适选择，执行机制负责落实硬性边界。

## 经验怎样从一次成功中形成

一次成功可能依赖临时条件：特定版本、缓存状态，或者恰好没有出现的数据。直接把整段过程固化成通用方法，容易扩大适用范围。

可复用经验需要包含适用条件、必要输入、执行步骤、验收办法与已知例外。后续使用中失败了，还要能够修订或停用。

Hermes 将记忆、历史搜索和技能积累放在持续使用的设计中。我们可以据此研究经验怎样被提取与再次采用；“经验积累是否持续改善任务成功率”仍属于实验问题。[参考 M02](../references/evidence.md#m02-hermes-的记忆与历史)

## 为什么要增加一个 Agent

可以先问希望隔离什么：输入资料、工具权限、专业指令，还是执行时间？

例如，一个执行者只读取日志并整理排查结果，另一个检查修复方案的影响范围。明确的任务边界有助于限制上下文和结果格式。若两个执行者需要不断交换全部信息，隔离的收益就可能被同步成本抵消。

给模型写上“研究员”“审查员”可以改变任务提示。实际权限仍需要工具和运行环境分别配置。

“隔离”也需要说清对象。Deep Agents 的一个默认子调用路径替换了父消息历史，却仍可传入文件等未被排除的状态，并回传允许的工作数据。[上下文装配专题](13-context-and-defaults.md) 说明这种上下文边界为何不等于所有资源和权限都已隔离。

## 委派与交接，控制权怎样转移

委派时，主执行者把子问题交出去，等待结果返回后继续组织整体任务。调用另一个 Agent 可以表现为一种工具能力。

交接时，后续处理转到另一个 Agent，由它承担新的对话或工作职责。交接需要传递目标、已知信息、约束和已经发生的动作。

OpenAI Agents SDK 同时提供 agents-as-tools 与 handoffs，分别组织工具式委派与交接。[协作系统专题](19-delegation-and-handoffs.md) 会沿固定实现说明控制与输入怎样转移；[执行预算专题](21-execution-budgets.md) 再用实际场景比较它们的轮数范围。[参考 S02](../references/evidence.md#s02-openai-agents-sdk-的协作概念)

## 并行带来的收益，需要减去协调成本

多个执行者可以同时阅读独立资料。最终还需要有人检查结果来源、处理重复与冲突，并判断覆盖是否完整。

若多个执行者同时修改同一份配置，就还要管理版本和写入冲突。若它们引用同一份错误资料，即使意见一致，也不构成独立验证。

因此，多 Agent 实验应同时记录总成本、等待时间、重复工作、汇总工作量和最终正确性。只测某个子任务的耗时，难以评价完整系统。

## 从两个不同的入口看协作

CrewAI 的材料区分以角色和任务组织的 Crews，以及更强调事件控制的 Flows。Deep Agents 提供子 Agent 与上下文隔离等默认机制。二者都可以成为协作案例，但默认机制和应用开发者承担的设计工作需要分别核对。[参考 S01](../references/evidence.md#s01-crewai-的协作与流程) · [参考 L02](../references/evidence.md#l02-langchain-生态层次)

判断协作是否有用，仍要追问：工作怎样拆分，子结果怎样核查，谁负责最终验收，以及增加执行者是否真的值得。预编排响应能帮助检查控制流，真实分工的质量和成本还需任务实验。
