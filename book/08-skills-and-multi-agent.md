# 第八章：Skills 与多 Agent——经验和分工怎样进入系统？

助手要比较高铁和住处。团队想到两种改进：把可靠的查资料方法整理给它，或者让两个助手分别查交通和酒店。

前一种是在复用做法，后一种是在分配工作。两者都可能有用，却解决不同问题。

## 一份 Skill，可以教助手怎样查

假如助手经常漏掉酒店页面的小字，可以写一份说明：先确认入住日期，再核对房型和完整费用，读取消条件，最后记录查询时间与原文位置。

把这种说明及相关脚本、示例放在一起，供适合的任务加载，就是一种 Skill。模型先看到名称与简介，需要时再读详细内容，不必每轮把所有说明都装进输入。

Pi、Goose 和 Hermes 有这种先列目录、再读正文的做法。Agno 还把说明、参考文件和脚本分别提供。读取脚本是看它怎么做，执行脚本则会真正运行代码，两者应分别检查许可。

还有更细的选择：Qwen 的条件技能会在开始处理匹配文件时才出现；ADK 可以让某些能力只暂时进入输入，用过或到期后再移出。这些机制减少无关说明，也要处理加载太晚、内容过期或刷新后失效的问题。

## 方法可以复用，一次价格不能永久照用

“查酒店时核对日期和完整费用”可以成为方法。“这家酒店一晚很便宜”却只是某次查询的结果，不能变成以后旅行都成立的规则。

复用说明应带适用条件和检查办法。网站改版、脚本失效或方法连续出错后，还要能够修订或停用。

同样，Skill 里写“查完直接订房”，也不能推翻用户这次不下单的要求。工作说明帮助模型选择做法，程序仍要检查真实动作是否允许。

## 两个助手出发前，要拿到同一份要求

可以请交通助手查周六去、周日回的高铁，请住宿助手查一晚安静住处。这样两边可能同时工作，减少等待。

但两者必须知道是同一个周末，也必须知道 1500 元是整趟旅行的总预算，不是各自可以花 1500 元。交通助手不能只查去程，住宿助手也不能把两晚的价格当成一晚。

```text
共同要求：上海到杭州，周末两天，周六住一晚，总预算1500元。
交通助手：比较往返高铁，注明日期、时间与费用。
住宿助手：比较一晚住处，注明可用日期、完整房价及安静程度的依据。
两者都不能订票、订房，日历也没有获得许可。
```

负责总稿的助手还要核对两份结果能不能放在一起：车到站时能否入住，两项费用加起来是否留得出吃饭与市内交通的钱。

## 分开对话，不等于分开权限

子助手可以只收到与自己相关的材料，避免在长对话里找重点。但少看一些聊天，不代表它无法访问父助手使用的文件或账号。

Deep Agents 的一种子调用会让子模型使用自己的消息，但程序仍可以把文件等信息传进去；Cline SDK 会为子助手传工具、策略和取消信号；Hermes 的委派可以跳过父方常驻记忆。要看它具体分开了什么，不能只看“独立助手”这个名称。

需要限制实际影响时，交通助手只给查询工具，住宿助手也不拿付款能力。角色名写成“研究员”，并不会自动缩小工具权限。

## 派出去等结果，还是把后续交给别人

委派时，总助手交出一个子问题，结果回来后继续写总稿。交通和住宿的分工适合这种方式。

交接时，后续处理转给另一个助手。比如一个助手接待用户，之后由专业助手继续整个对话。它需要带走目标、限制和已经发生的动作。

OpenAI Agents SDK 明确区分工具式委派和 handoff；LlamaIndex 的工作流也会在交接后改变当前助手。Aider 的方案与编辑则是串行分工，结果回到原过程。助手数量相同，后续由谁负责可能不同。

## 并行省下的时间，还要减去核对工作

两边同时查询可能更快，却也可能查了重复内容、用了不同日期，或者都依赖同一条过时信息。两份意见一致，不足以成为两次独立验证。

不同项目会采用管理者派任务、轮流选发言者，或同一成员串行、不同成员并行等安排。选择哪种，要看工作是否真的能分开，而不是先给系统设计许多职位。

这次旅行可以先拆成两项独立查询，让总助手负责费用合计和完整性检查。如果两边必须不断交换全部网页，单个助手直接完成也许更省事。

现在材料开始汇总。即使两个助手都说“完成”，总稿仍可能漏掉周日怎么回家。下一章就看这一次漏项怎样被发现。
