# 第八章：Skills 与多 Agent——经验和分工怎样进入系统？

R42 的计划里有两条可并行的调查线：一条核对日志与配置，另一条核对源分区和数据范围。团队手里也有过去排查留下的工作说明，希望助手复用其中可靠的做法。

这里有两个方向：把经验整理为可加载的工作方法，以及把任务组织为多个执行者之间的协作。它们可以结合，却承担不同责任。

## Skills 怎样把经验变得可复用

Skill 可以把一类工作的说明与辅助材料放在一起。Pi、Goose、Hermes 等项目先列名称和描述，再在需要时读取正文；Agno 还将说明、参考资料和脚本分别暴露。读取脚本与执行脚本是两种动作，应有不同边界。

一份排查 Skill 可以写明：先确认环境与日期，怎样选择日志，遇到哪些异常要停止自动修改，最后用什么方法验收。它还可以带示例、脚本与检查材料。

这使经验有了明确位置，也减少每轮携带全部细节的负担。可见性还可以更细：Qwen 的条件技能在触及匹配文件后才出现；ADK 的能力加载有作用时限和淘汰机制。省下常驻输入的代价，是系统必须正确处理发现、加载、刷新和失效。

如果一项约束必须在任何情况下强制执行，应当把它落实到权限或工具检查中。工作说明可以帮助模型做出合适选择，执行机制负责落实硬性边界。

## 经验怎样从一次成功中形成

一次成功可能依赖临时条件：特定版本、缓存状态，或者恰好没有出现的数据。直接把整段过程固化成通用方法，容易扩大适用范围。

可复用经验需要包含适用条件、必要输入、执行步骤、验收办法与已知例外。后续使用中失败了，还要能够修订或停用。

一次排查产生的“字段映射有误”是这次任务的发现；“先对齐运行编号，再核对日志、配置和源结构”才可能成为复用方法。前者进入任务记录，后者还需补上适用场景、工具要求与验收办法，经过复核再加入技能目录。自动提取可以协助整理，采用和停用仍要有明确依据。

## 为什么要增加一个 Agent

可以先问希望隔离什么：输入资料、工具权限、专业指令，还是执行时间？

例如，让日志研究者核对 E42 与 v6，让数据研究者核对源分区。若前者读的是测试运行，后者读的是生产 run-807，两份报告即使各自合理，也无法合成 R42 的结论。因此，两者出发前应共享报表、业务日期、运行编号和“生产只读，测试验证”的约定；结果返回后，由协调者核查证据。

给模型写上“研究员”“审查员”可以改变任务提示。实际权限仍需要工具和运行环境分别配置。

“隔离”也要说清对象。Deep Agents 的一种子调用会换掉父消息历史，却仍可传入文件等状态；Cline SDK 为子 Agent明确传递工具集、策略和取消信号；Hermes 的委派可以跳过父方常驻记忆和上下文文件。子任务少看一些对话，与子进程无法访问某个目录，属于不同保证。

## 委派与交接，控制权怎样转移

委派时，主执行者把子问题交出去，等待结果返回后继续组织整体任务。调用另一个 Agent 可以表现为一种工具能力。

交接时，后续处理转到另一个 Agent，由它承担新的对话或工作职责。交接需要传递目标、已知信息、约束和已经发生的动作。

OpenAI Agents SDK 通过 Agent 工具和 handoff 明确区分两者；LlamaIndex 的工作流也会在交接后改变当前执行 Agent。Aider 的 Architect/Editor 则是串行方案与编辑分工，编辑结果还要回到原过程。角色数量相同，控制权走向可能完全不同。

## 并行带来的收益，需要减去协调成本

多个执行者可以同时阅读独立资料。最终还需要有人检查结果来源、处理重复与冲突，并判断覆盖是否完整。

若多个执行者同时修改同一份配置，就还要管理版本和写入冲突。若它们引用同一份错误资料，即使意见一致，也不构成独立验证。

因此，多 Agent 实验应同时记录总成本、等待时间、重复工作、汇总工作量和最终正确性。只测某个子任务的耗时，难以评价完整系统。

## 从不同的组织方式看协作

CrewAI 的任务组织可以采用顺序或管理者分派；AutoGen 的选择团队则先用程序规则筛选，再决定下一个发言者；AgentScope 的团队可以把同成员任务串行、不同成员任务并行。它们分别在组织任务、调度对话和安排执行。设计时应选自己真正需要的控制单位，避免为两个独立查询先建一套庞大组织。

对 R42，可以先让两条独立读取任务并行，把测试配置修改与最终交付留给协调者组织。这样可能缩短等待，却增加任务契约和证据核查的成本；两条调查若必须频繁共享原始材料，单个连续上下文反而更容易管理。预编排响应能检查控制流，真实分工的收益仍要用任务实验判断。

即使两位研究者给出了相同建议，任务也没有自动完成。下一步要把建议放到测试环境里，检查产物，并决定什么证据足以支撑那句“可以交付”。
