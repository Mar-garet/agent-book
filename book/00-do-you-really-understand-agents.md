# 开篇：你真的懂 Agent 吗？

早上九点，你对一个 AI 助手说：

> 昨晚的报表又失败了。帮我找到原因，准备修复方案，确认可行后告诉我。

它打开日志，找到异常，阅读相关文件，修改了一段配置，重新运行任务。几分钟后，它回复：“问题已经解决。”

整个过程很像一个同事在工作。你可能会觉得，自己已经知道 Agent 是什么：一个能够使用工具、自己完成任务的 AI。

现在，把这个故事稍微改一下。

它看到的日志来自测试环境，失败的报表却在生产环境。它重新运行的任务返回成功，但生成的结果缺了最后一天。它在昨天的聊天记录里找到“可以直接修改配置”，却没有发现，那次授权只适用于一个临时实验。

它依然回复：“问题已经解决。”

你会发现，刚才那个定义还不足以帮助你判断：这个 Agent 究竟完成了什么。

## 那句“已经解决”，是谁给出的？

模型生成了这句话。模型依据的信息，却来自另一整套系统。

某个程序决定给模型哪些日志；某个工具执行了查询；某个权限规则允许了修改；某个状态记录保存了运行结果；也可能没有任何环节核查最终报表，模型就根据一条成功消息结束了任务。

一次任务看起来是 AI 完成的，责任却分布在许多地方。要理解 Agent，我们需要沿着这条责任链追问。

日志里的信息准确吗？工具参数指向了正确的环境吗？超时代表失败，还是执行成功后没有收到响应？模型可以建议修改，但谁有权允许修改？一段旧记录为什么有资格影响今天的行动？

这些问题会决定系统的行为。换一个更强的模型，可能改善其中一些环节；另一些问题需要重新设计运行机制。

## 先把“聪明”拆开来看

假设两个系统使用同一个模型。

第一个系统每次把全部聊天记录发送给模型，允许模型自由选择命令，最后由模型判断是否完成。

第二个系统先明确报表日期与环境，只提供相关日志，给写操作设置范围，保存每一步状态，并在结束前核对数据是否完整。

两个系统的差异可以出现在模型之外：信息选择、动作边界、状态保存和结果验证，都会影响最终表现。

这里没有预设第二个系统在所有任务上都更好。额外检查会带来时间和成本；固定的约束也可能限制探索。重要的是，你已经能够说出差异在哪里，以及应该怎样验证它是否值得。

本书希望带你获得这种能力。

## 一张计划表，会自己把事情做完吗？

你可能见过 Agent 先列出计划：查日志、定位错误、修改配置、重新运行、检查结果。

计划给了任务一个可读的形状。真正执行时，日志可能没有权限，错误可能无法复现，修改可能影响另一张报表。系统必须决定要不要改计划、补充信息、等待用户，或者结束当前尝试。

因此，我们不能只看 Agent 在顺利时列出了多少步骤。还要看情况变化后，它如何重新认识问题。

同样，一次工具调用证明系统尝试了一个动作；一次存储证明信息留下了痕迹；多个角色证明系统进行了某种分工。要进一步判断它们的作用，还需要看反馈、读取和协调的过程。

## 为什么要一起看这么多开源项目？

因为不同项目把责任放在了不同地方。

Pi 将自身描述为可扩展的极简运行系统，并把一些工作方式留给扩展。Deep Agents 为长任务提供更多默认机制。LangGraph 关注有状态的执行过程。OpenClaw 让持久信息进入工作区文件。Hermes 将记忆、历史检索和技能积累放进持续使用的体验里。它们的材料会在后文逐项展开。[项目资料](../references/evidence.md)

我们会拿同一个问题去问它们：如果任务中断了，谁知道已经做到哪一步？如果检索到一条旧规则，谁判断它是否仍然有效？如果一个动作产生了外部影响，谁确认它已经发生？

项目之间的差异，会帮助我们看见 Agent 设计中的选择。某些项目还处在不同层次：一个提供现成的工作体验，另一个提供搭建体验的基础。只有先弄清它们分别承担什么责任，比较才有意义。

## 我们怎样判断自己真的理解了？

你不需要先记住三十二个项目的功能，也不需要先学会所有框架的调用方式。

可以从解释一个具体过程开始：用户提出目标，运行系统准备上下文，模型选择动作，执行器检查并调用工具，环境返回结果，系统更新状态，再决定是否继续。

接着，在这个过程中拿走一样东西。

拿走反馈，它还能知道行动的后果吗？拿走状态，它还能在中断后继续吗？拿走权限检查，它还能限制自己的影响范围吗？把有用信息压缩掉，它还能做出相同判断吗？

当你能够解释这些变化，并据此提出实验，你就开始拥有自己的 Agent 判断标准。

本书将沿着这条路，从第一次行动，走到一个系统如何长期、可靠地工作。
