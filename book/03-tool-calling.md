# 第三章：工具调用——一次请求，几层责任

助手已经找到一班较合适的去程高铁，开始比较住处。此时工具列表里有一个叫作“酒店”的工具，只接受酒店名称。

调用它，会搜索价格、查看房型，还是直接订房？用户说过不订房，模型却可能从这个含糊的名字里猜错。

工具的约定要比名字具体。模型要知道自己能请求什么，程序也要知道这次请求到底会做什么。

## 描述、请求和执行，不是一件事

应用先向模型描述工具：可以查询哪些内容，必须提供哪些参数。模型再提出请求，例如“查这家酒店周六入住、周日退房的一间房”。

运行程序检查请求，随后调用酒店服务。真正查询房价的是工具背后的代码，模型不靠写一句“我查到了”就能拿到新数据。

如果原有酒店服务的接口很复杂，开发者可以写一层转换代码，把简洁的查询变成服务需要的参数，再把结果整理回来。这层代码称为“业务适配器”。它负责连接已有系统，不负责替模型决定行程。

## 把容易猜错的条件写进参数

查询住处至少要带入住和退房日期、人数与房间数。如果只写“住一晚”，服务可能采用默认日期；如果模型选错周末，格式正确也没有用。

程序因此要做几种检查。日期写法是否合法，是格式检查；退房是否晚于入住，是业务检查；用户是否允许提交订单，是权限检查。

这次只准备草稿，可以只开放查询工具，不提供订房工具。需要订票时，先由用户提出新的要求，再开放相应动作。这样少了一些临场便利，却避免把“找到合适房间”直接变成“已经付钱”。

## 返回“成功”，要说明成功了什么

搜索请求正常结束，不代表找到了可入住的房间。一家酒店有网页，也不代表那天有房。工具应分别返回“查询失败”“查询成功但无房”和“找到可用房型”。

价格也要带上它对应的日期、房型、费用说明和查询时间。否则助手可能拿另一晚的低价来算这次预算。

这些区别会影响下一步：网络临时出错可以稍后重查；没有房就换一家；需要登录才能看价格时，应说明暂时无法确认。把所有情况都变成空列表，会让模型把“没查到”误读为“根本没有”。

## 通用工具和专门工具，各有什么代价

浏览器能读许多网站，适合找不熟悉的资料。但模型还要自己理解页面、辨认价格和找到日期。

专门的房价查询工具可以直接返回某个周末的可用房型，省去读网页的细节。代价是开发者要维护接口，它也未必覆盖所有酒店。

这次旅行可以同时用两者：浏览器找候选住处，专门工具核对日期和费用。读到页面上的促销，仍要回到这次入住条件，不能直接拿最低价作结论。

## 行动也可以写成代码

模型可以一次请求查一家酒店，也可以生成一小段代码，逐个查询几家并比较结果。smolagents 的代码行动提供了后一种做法，同时也有其他调用方式。

代码适合表达循环与汇总，可能减少模型反复发请求的次数。执行环境却要控制代码能访问什么，出错时也要能查清停在哪一步。

其他任务还会采用不同形式。Aider 让模型按编辑格式提出修改，再由程序解析、应用并检查；Browser Use 则根据当前页面选择浏览器动作。它们都在让模型表达行动，执行代码理解的内容却不同。

因此，选择工具形式要看任务。重复查询适合组合，付款和写日历等动作则适合有清楚参数、许可和结果的专门接口。

## 查询重试，与再次提交有区别

酒店页面读取失败，可以再读一次。订单提交后没有收到回复，却不能马上再订一次，因为第一份订单可能已经生成。

未来用户若同意添加日历，也会遇到同样问题：页面卡住，不等于日程没有创建。程序应先查上一次结果，再决定是否重做。重复请求同一件事却不产生重复效果，称为“幂等”；它需要工具和服务一起设计。

即使一轮提出多个工具请求，也要安排好顺序。交通与住宿查询可以同时进行，付款则不应混进这批查询。Cline SDK 区分相邻的并行调用与顺序调用；Gemini 会在工具前钩子改过参数后再检查策略。这些都是工具名字之外的执行安排。

助手现在能明确地查询，能分清无房与查询失败，也不会把看房价变成下单。接下来，若换一个助手应用，怎样复用已经接好的这些服务？
