# 第三章：工具调用——一次请求，几层责任

助手已经从正确的日志里读到错误 E42，接下来要核对字段映射。此时，工具清单里有一个叫作 `重新运行报表` 的能力，只接受报表名称和日期。

模型很容易把它当作验证方案的下一步。但参数里没有环境：它究竟会重跑测试任务，还是改动生产？即使工具返回“成功”，也可能只表示进入队列。值班工程师要求的测试验证，还没有发生。

工具名称很短，真实约定可能很长。

## 模型提出请求，执行器把请求变成行动

典型的工具调用有一条清晰的责任链：应用描述可用能力，模型输出工具名与参数，运行系统检查请求，执行器调用具体能力，工具返回结果，系统将结果整理为下一轮观察。

这里有三种容易混淆的东西。工具描述告诉模型“能做什么”；工具请求表达“希望这次做什么”；工具实现负责实际访问文件或服务。工具描述本身不会执行任务。

应用通常还需要业务适配器：把 Agent 的通用请求转换为已有系统的调用，并把业务结果转换回来。例如，日志查询工具背后要对接公司现有的日志服务。这一层可以独立于模型替换。

## 好工具要让重要约束变得明确

报表工具可以要求调用者明确选择环境、日期区间与输出目标。运行系统还能从可信的任务状态中固定部分参数，避免由模型随意生成。

参数结构只能解决其中一层问题。一个字段满足日期格式，不代表它是用户授权的日期。一个用户编号存在，也不代表当前任务可以读取该用户的数据。

因此，结构校验、业务校验和权限校验承担不同责任。它们可以在不同位置实现，但需要形成完整路径。

## 工具返回结果，也应帮助系统判断下一步

“成功”可能代表请求被接受、后台任务已启动，也可能代表结果已经生成。调用者需要分辨这些阶段。

有用的反馈会保留实际状态、任务编号、检查范围、可验证的产物，以及错误是否适合重试。反馈不必包含所有原始细节，但不能把“没有权限”和“没有数据”合并成同一个空结果。

模型可以解释错误，运行系统也可以对某些错误采用固定策略。短暂的连接问题与过期凭证，通常需要不同的处理方式。

## 工具越通用，调用者承担的判断越多

命令行工具可以组合大量已有能力，适合探索性强的工作。与此同时，调用者需要自己组织命令、理解输出，并承担更广的操作语义。

一个边界明确的业务工具可以在内部完成校验和状态查询。调用者需要掌握的细节减少，但工具的适用范围也会收窄，业务方需要维护它。

对 R42 的调查，可以保留受限的通用读取工具，让助手探索线索；到了测试重跑，就值得使用明确要求环境、业务日期并返回任务编号的业务工具。前者保留探索空间，后者需要业务方维护，却能减少关键动作中的歧义。

## 行动可以用结构化参数，也可以用代码表达

常见方式是让模型输出一个工具名和一组结构化参数，由执行器分派调用。

另一种方式是让模型生成一小段代码，在受约束的执行环境里组合工具。smolagents 的材料将这种代码行动作为重要设计方向，同时也提供其他调用方式。

例如，需要对多个日期执行相同查询时，代码可以表达循环与汇总；单个业务动作则可以用一次明确请求表达。我们由此得到一个待验证的问题：减少模型与工具之间的往返，是否抵消了代码执行、调试和隔离所增加的成本？

这里的选择不只两种。Aider 让模型按编辑协议给出修改，程序解析、预演并应用，再把检查错误交回；Browser Use 先根据页面状态选择浏览器动作，页面变了就需要重新观察。它们与函数调用都在表达行动，执行器理解的单位却分别是补丁、浏览器动作和业务请求。

因此，代码行动不等同于“用于写代码的 Agent”。为 R42 选择动作形式时，可以让临时的多日期读取用代码组合，把测试重跑保留为明确的业务调用。这样保留探索弹性，也让关键写入有稳定身份；代价是维护两种执行与错误反馈路径。

## 写操作会让重试变成系统问题

读取文件失败后重试，通常只是再读一次。创建任务、发送通知或写入数据失败后重试，则可能重复产生影响。

如果远端已经创建任务，但响应丢失，调用者面对的是“不知道是否成功”。这时应优先查询状态，或使用能够识别重复请求的机制。幂等指同一业务动作被重复请求时，不会重复产生本不该重复的效果；它需要工具和业务系统共同设计。

把“出错就再试一次”写进提示词，无法独自完成这件事。

## 从概念继续到真实执行链

一次模型输出也可能带来多项动作。先检查所有请求再执行，与检查一项就执行一项，会产生不同的暂停边界；并行读取节省等待，并行修改同一配置则可能互相覆盖。

Cline SDK 把相邻的可并行调用组成一组，顺序工具成为前后两组之间的屏障。Gemini 的调度器在工具前钩子改过参数后，再执行策略判断。Pi 则把核心循环与宿主的工具前拦截分开。这些设计都说明：决定调用顺序、检查最终参数、接住错误，是执行器的工作，单看工具描述看不出来。

R42 的第一版可以先让独立查询并行，修改和重跑串行。若一个查询失败，保留其他查询已经取得的证据，再决定补查；不为了重试一项而重复整批。

至此，R42 的工具约定可以区分生产读取与测试重跑，也能保留后续测试任务的查询凭据。团队接下来遇到的是连接问题：日志平台和报表平台各有接口，换一个 Agent 应用，难道还要重新适配一遍？
