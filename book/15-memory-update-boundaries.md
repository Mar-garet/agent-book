# 记忆系统：从项目比较到写入、检索与更新

助手正在补那份还缺周日返程的杭州行程。用户先前已经补充过：“我喜欢安静一点的住处。11 月起，旅行预算可以提高到 2000 元，但这次周末仍然是 1500 元。”

助手回复“记住了”。过几天，用户换个会话继续讨论，它却又推荐热闹街区的酒店。再看另一次回答，助手记住了 2000 元，却把这次行程也按 2000 元安排。

这两个错误方向相反：该留下的偏好没有留下，不该提前使用的新预算却用上了。把聊天全部存进数据库，不能自动解决其中任何一个。

为了说明规则何时适用，这里补上一个日期：本次从上海出发去杭州的时间是 10 月 24 日。即使用户到 11 月才回来修改这份行程，本次预算也仍是 1500 元。

## 要记住偏好，还是记住做到哪里了

“喜欢安静的住处”可能对以后许多次旅行都有用。“还没选周日返程车次”只描述这一次旅行的进度。已经生成的订单又是外部服务里的记录，不能靠助手写一句“已订好”就算数。

因此，开发者至少要分开保存三类信息：用户说过什么，以后还应采用哪些偏好，以及这次任务做到了哪里。模型回答之前，程序再从这些记录里挑出本次需要的内容。

这也是“记忆”这个名字容易让人误解的地方。OpenAI Agents SDK 的 Session 主要保存对话条目；smolagents 会保存任务、行动与计划步骤；Aider 可以恢复先前聊天。这些功能帮助助手接着工作，却不意味着它们已经自动归纳出一份正确的用户偏好。

> [!IMPORTANT]
> “文件里有这句话”“这次找到了这句话”“模型收到了这句话”“模型按它做了”，需要分别检查。

假设偏好文件已经写着“住处要安静”，但本次请求没把它读进来，问题出在读取。如果输入已经包含这条偏好，助手仍选了夜市楼上的酒店，就要继续检查它怎样挑选，以及程序有没有核对结果。

```mermaid
%% 一条偏好怎样影响下一次推荐
flowchart LR
    A[用户说明] --> B[决定保留]
    B --> C[写入记录]
    C --> D[下次读取]
    D --> E[交给模型]
    E --> F[核对推荐]
```

## 偏好不多时，直接维护一份短文件

个人助手可以先有一份简短的偏好文件，例如：“住宿优先安静；预算调整必须保留适用日期。”用户能查看，助手也不必每次翻几百轮聊天。

Hermes 的内置精选记忆就提供这种思路。模型提出增加、局部修改或删除，程序检查改哪一段、长度是否合适，再保存。一次修改多处时，也有整批提交的处理，避免只改了一半。

程序能检查修改过程，却未必知道偏好是否归纳正确。用户说“这次想住热闹一点”，不应被直接改写成“以后都喜欢热闹”。决定长期保存之前，还要保留“这次”这样的条件。

文件更新后，还需问模型什么时候能读到。Hermes 的文件内容与用于提示的已加载内容有各自的刷新时机。用户刚说完时，模型可以从当前聊天知道新偏好；换到一个不重复原话的任务，才更容易看出长期记忆是否真的起作用。

AutoGen 的可选 ListMemory 展示了更简单的做法：把列表里的内容全部交给模型。十条偏好时很直观，几千条历史时就会占满输入。小规模可以先用这种设计，资料增长之后再增加筛选，不必一开始就建复杂检索系统。

## 资料很多时，先给目录，需要时再读

如果用户积累了许多城市攻略、住宿偏好和过往旅行记录，每次全部发送会很浪费。程序可以先给模型一份目录，再按当前问题读取相关内容。这里的“检索”，就是从一大批资料里找出这次可能用得上的部分。

OpenClaw 的 memory-core 插件将查找与读取分开：先找相关片段，再取需要的原文；精选内容仍可以通过文件工具修改。搜索能否包含历史会话，取决于宿主配置，模型不能仅靠修改参数就扩大允许查找的范围。

AgentScope 的可选文件记忆中间层会把限量的 MEMORY.md 内容放进系统提示，也可以让模型查看主题文件的简要目录，再选择要读哪份。这比全部加载省空间，但选错文件就可能漏掉偏好。开发者仍需让助手在找不到资料时承认缺口。

Letta Code 的公开本地实现还用 Git 管理记忆。Git 用来记录文件的修订；“提交”就是把这次修改登记成一个可识别的版本。记忆目录最外层的文件作为常用内容，较深目录按需读取，组装输入时以已经提交的文件为准。

因此，只改了文件、还没提交的内容，可能没有进入这次输入。提交改变后，程序可以在后续对话里补充更新，而不必重写整段旧提示。托管服务内部是否采用同样过程，不能只从这份本地实现推断。

这类设计适合“资料很多，每次只用一小部分”的助手。代价是多一次查找或读取，还要保证返回的文件位置确实能打开。给出一个路径，却让下一次会话读不到，不算保留好了知识。

## 助手也可以自己整理历史，但整理不等于采用

另一条路是让后台程序阅读过去的工作，找出值得保留的经验。用户不必亲自维护每条偏好，但系统必须决定哪些只是建议，哪些可以写进以后都采用的记录。

Codex 的记忆写入分成提取和整合两步。符合条件、由用户直接开启的会话可以启动后台工作；子助手的会话不因此自动启动同一流程。程序先领取一部分历史运行记录，提取候选，再整合进记忆。领取时还记录由谁处理、依据哪个来源版本，防止较早开始的工作覆盖较新的内容。下次读取另走自己的流程，所以后台已经启动，并不等于新记忆立刻生效。

Gemini CLI 的 Auto Memory 路径让人参与采用。后台服务在满足条件时检查历史，产生待审候选；采用修改前要检查文件和允许范围，然后刷新记忆。好处是重要变化可以审阅，代价是用户需要处理待审内容。

Qwen Code 则要协调正在进行的提取和新来的查询。主助手已经写过记忆时，可以跳过重复提取；同项目的新请求要与旧提取协调；新查询也可以取消旧的预先检索。这些安排解决的是“别让旧工作抢在新问题前面”，不能独自保证归纳内容准确。

所以，后台整理适合降低维护负担，却应谨慎处理重要规则。“这次酒店看起来不错”可以暂存为一条观察，“以后所有旅行都住这里”就需要更充分的依据。一次查到的价格尤其不能变成永久偏好。

## 规则很精确时，别只存一段话

“11 月起预算提高到 2000 元”包含金额和起始日期。如果只保留“预算 2000”，程序就丢掉了决定本次该用哪条规则的关键条件。

开发者可以把旅行预算保存成明确的记录：属于哪个用户，金额多少，从哪天开始，到哪天结束，依据用户哪句话。LangGraph 的 Store 允许应用自己定义这类记录，并与“任务做到哪里”的检查点分开配置。Python 与 JavaScript 实现都体现了这种分工；存储接口不会替应用决定预算规则。

有些框架提供更多组织方法。LlamaIndex 可以分别管理近期聊天和长期记忆块，读取时再挑选、排列。CrewAI 的统一 Memory 会在检索前等待已经排队的写入完成，减少“刚保存却还读不到”的情况。这些程序安排能让读写更可靠，仍不能判断一条旅行规则应适用于哪一天。

多人或多任务共享资料时，还要分清是谁的记忆。Agno 的用户记忆更新需要配置相应管理器和开关；Mastra 区分本次对话与某个用户的资料；ADK 的内存记忆按应用和用户组织。开发者不能只加一个用户编号就认为权限已经解决，还要让读取服务实际检查调用者能否访问。

## 新规则有两个“生效时间”

第一种时间，是程序什么时候把新规则交给模型。第二种时间，是新规则从哪次旅行开始适用。两者不能混在一起。

| 记录或输入 | 内容 | 本次应该怎样处理 |
| --- | --- | --- |
| 原预算 | 11 月前出发的旅行，预算 1500 元 | 10 月 24 日这次仍使用它 |
| 新预算 | 11 月起出发的旅行，预算 2000 元 | 留给之后的旅行 |
| 没刷新的输入 | 只有原预算 | 11 月新任务可能还没读到调整 |
| 完整的新输入 | 两条预算和各自日期 | 按本次出发日期选择 |

OpenCode 会记录项目说明等持续使用的指令发生了哪些变化，保留当时读到的文字与版本。Deep Agents 则可以暂存已经读到的文件内容，这份副本称为缓存；已有缓存时，同一路径不会再次下载。一个主动记录变化，一个可能继续用已读副本，开发者需要清楚自己采用哪种方式。

下面两段代码只做一件事：根据出发日期选择预算。每条规则包含开始日期和结束日期；开始日算在内，结束日不算。要求恰好找到一条，避免规则有空档或互相重叠时悄悄选错。日期格式在示例中固定，真实应用还需检查输入格式与用户身份。

```typescript
type TravelBudget = { amount: number; from: string; until: string | null };
const budgets: TravelBudget[] = [
  { amount: 1500, from: "2020-01-01", until: "2026-11-01" },
  { amount: 2000, from: "2026-11-01", until: null },
];
function budgetFor(departure: string): number {
  const found = budgets.filter(b => b.from <= departure && (b.until === null || departure < b.until));
  if (found.length !== 1) throw new Error("budget gap or overlap");
  return found[0].amount;
}
for (const departure of ["2026-10-24", "2026-11-07"]) {
  console.log(`${departure}=${budgetFor(departure)}`);
}
```
```python
budgets = [
    {"amount": 1500, "from": "2020-01-01", "until": "2026-11-01"},
    {"amount": 2000, "from": "2026-11-01", "until": None},
]
def budget_for(departure):
    found = [b for b in budgets if b["from"] <= departure
             and (b["until"] is None or departure < b["until"])]
    if len(found) != 1:
        raise ValueError("budget gap or overlap")
    return found[0]["amount"]
for departure in ["2026-10-24", "2026-11-07"]:
    print(f"{departure}={budget_for(departure)}")
```

代码看的是出发日，而不是今天。如果用户到 11 月才修改 10 月 24 日那份行程，程序也不会自动把它放宽到 2000 元。是否改变这次预算，应由用户另作说明。

## 为这位旅行助手选择第一版记忆

可以先用短文件保存“喜欢安静住处”一类稳定偏好，用带日期的记录保存旅行预算，再单独记下这次缺少周日返程。前两类供以后旅行参考，后一类帮助当前任务接着做。

资料增多后，再增加目录和检索；反复同类工作很多时，再考虑后台提炼。每增加一种机制，都要回答一个具体问题：它从哪里读，写到哪里，用户改正之后，下次什么时候会用到新内容？

检查也从这些问题开始。换个会话，不重复“住处要安静”，看推荐时是否确实采用了偏好；拿 10 月和 11 月两次旅行，检查预算选择是否不同。若文件正确而模型没收到，修读取；若模型已收到却用错，修选择和最终核对。这里给出的是验证方法，没有声称本书实际跑过旅行服务。

现在，助手知道长期偏好与本次进度各放哪里，也不会提前使用 11 月的新预算。它还得处理眼前很长的酒店与车次网页：下一次回答究竟需要读到哪些内容？
