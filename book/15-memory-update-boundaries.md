# 记忆系统：从项目比较到写入、检索与更新

经营日报 R42 还在排查中，值班工程师补充了一条约定：“报表现在按上海时区计算，从下周一开始改成东京时区。”助手把新规则写进记忆，回复“已记住”。

先预演下周一的一次新任务：助手仍按上海时区准备查询。工程师打开文件，东京时区明明就在里面。究竟是谁忘了？

直接把所有“上海”替换成“东京”也会犯错。R42 的业务日期是 10 月 16 日，核对窗口是 15–16 日；即使下周一才重跑，也仍应使用旧口径。我们需要让新任务获得新规则，同时保住历史任务的含义。

这段教学情境里，下周一是 2026 年 10 月 19 日。困难不是少了一处存储，而是同一条信息穿过了保存、整理、检索与请求组装，每一步都有自己的责任与时间。

## “已经记住”至少有四种意思

聊天记录保存“用户说过什么”；执行检查点保存“任务做到哪里”；长期记忆保留“以后仍值得使用什么”；上下文是“模型这一轮实际收到什么”。它们可能存进同一个数据库，却不会自动互相转换。

R42 恢复时，要知道 run-807 已查过哪些日志，这是执行状态。下一周期开始时，要取得项目时区，这是跨任务事实。发出查询之前，还要把适用于业务日期的规则送进本次输入，这是上下文组装。

OpenAI Agents SDK 的 Session 接口主要保留会话条目，smolagents 的 memory 保存任务、行动与计划步骤，Aider 可以恢复聊天历史。它们都有助于延续工作，却不能仅凭“memory”这个名字，就推断系统已经会提炼并更新长期事实。

> [!IMPORTANT]
> 保存成功、取回成功、进入本次输入、被正确使用，是四次不同的判断。排查遗忘时，先找出断在了哪一步。

```mermaid
%% 从用户纠正到下一次行动

    A[候选事实] --> B[校验提交]
    B --> C[权威记录]

```

权威记录指应用用来决定当前事实的版本。它可以是人能编辑的文件，也可以是有明确键与版本的数据库记录；关键是后续索引、摘要与缓存都知道自己依据哪一版。

## 第一种设计：把少量常用信息整理给模型

个人助手常用的偏好不多，直接维护一份精选记忆很有吸引力：用户能查看，模型能修改，新任务不必重新翻整段历史。

Hermes 的内置记忆工具沿着这条思路工作。模型提出增加、局部修改或删除，程序检查目标、匹配片段与容量，再交存储提交；批次编辑也有整体提交边界。它把“值得记住什么”的判断交给模型，把“这次能否可靠改动”交给程序。

但文件写入和模型输入仍是两件事。Hermes 的精选内容与提示快照有各自的刷新边界；用户刚纠正时，当前对话本身还包含新规则，真正暴露记忆链问题的，往往是不再重复原话的新任务。

AutoGen 的可选 ListMemory 则提供了更直接的对照：查询返回列表中的全部内容，再按顺序加入模型上下文。它简单、容易理解，适合很小的资料集；资料一多，全部注入就会挤占任务空间。简单方案的代价不是“不够智能”，而是将筛选责任留给了调用者或模型。

因此，第一版个人助手可以先用精选文件，但要给它一个明确的大小上限与加载时机。几十条稳定偏好值得常驻，几千条项目历史就应另找读取方式。

## 第二种设计：文件作为知识，目录与检索负责找路

团队资料增多后，全文常驻不再合适。系统需要先告诉模型“有哪些材料”，再在具体任务中取得相关部分。

OpenClaw 的 memory-core 插件把精选文件、检索索引与读取片段组织起来：检索工具找候选，读取工具取原文，精选写入仍可经过文件工具。会话历史能否进入搜索，还受宿主配置与可信运行范围控制；模型不能靠改一个搜索参数自行扩大来源。

AgentScope 的可选文件记忆中间层，会将有界的 MEMORY.md 放进系统提示，还可以让模型从主题文件的头部目录中选择相关文件。它适合让人审阅和维护知识，但目录本身也占预算，模型选错文件时仍可能漏掉事实。

现行 Letta Code 的本地 MemFS v2 又作了一个鲜明选择：根层记忆进入常驻内容，较深材料延迟读取。它以 Git 的已提交版本编译记忆；工作区改了但没提交，与模型读到的记忆版本可以不同。提交变化后，本地后端还能通过会话中的更新片段传递新记忆，而不必把旧前缀全部改写。这里说的是公开的本地实现，不能据此推断托管服务内部采取相同过程。

这几种设计都让“知识很多”与“当前输入很小”共存，代价是多出一段找路过程。系统必须让模型知道为什么回查、回查哪里，以及找不到时如何承认缺口。一个看起来像文件路径的字符串，只有在当前权限与保存期限内确实可读，才是一条有效的证据线索。

## 第三种设计：从工作历史中提炼，而不是等用户逐条维护

如果助手不断重复同类工作，让用户亲自维护每条经验会很累。后台提炼可以从合格历史中找候选，再整理为更紧凑的知识。难点随之从“能否写入”变成“谁决定采用，以及何时生效”。

Codex 的记忆写入是一条分阶段管线：合格根会话启动后台工作，先从历史运行记录提取候选，再由另一阶段整合。候选领取有租约与来源版本，整合也有自己的工作区和提交处理；读取侧再按记忆版本组织摘要与提示。这不是模型每说一句话就直接覆盖长期规则。它减少前台整理负担，也引入提取、整合与读取之间的延迟。

Gemini CLI 的 Auto Memory 路径把人保留在采用环节。后台服务对合格历史做提取，受项目锁和节流约束，结果可以进入待审候选；采用补丁要检查目标和允许范围，随后再刷新记忆。它把可审阅性放在即时生效之前，代价是用户需要处理积压候选。

Qwen Code 的管理器组织提取、整理与召回：调度受开关和触发条件控制，主 Agent 已经写过记忆时可以跳过重复提取；正在运行的项目提取与后来请求还要协调。前台新查询会取消旧预取，避免过时召回占住当前任务。后台作业完成与当前请求采用结果，是两个状态。

这些例子说明，后台提炼并没有取消写入政策，只是换了提出候选的人。影响大的项目口径应保留可核对的来源，模糊的习惯可以暂存候选，一次临时请求则不应轻易变成永久规则。

## 第四种设计：由业务应用明确事实的结构

报表时区、合同适用范围、客户权限都有精确含义，不能只靠一段自由文本承载。应用可以把事实组织成有对象、来源、版本和有效期的记录，再选择适合的存储接口。

LangGraph 的 Store 用命名空间与键表达记录，Python 与 JavaScript 实现都把存储配置与执行检查点分开。语义搜索是可选择的能力，不是每个后端都会自动启用。LangChain 的装配层也把这些设施交给调用者配置。

LlamaIndex 的 Memory 可以把活动聊天与长期记忆块分开，超预算后将旧消息交给相应块处理，读取时再按优先级组装。CrewAI 的统一 Memory 则提供写入队列与检索前的读屏障，并区分直接搜索和更深入的查询流程。前者强调不同记忆表示的组合，后者让写入与后续读取的先后关系更清楚；两者都不能仅靠存储结构判断业务事实正确。

Agno 的用户记忆更新需要配置管理器与相应开关，Mastra 的召回区分线程范围和资源范围，ADK 的内存记忆按应用与用户组织。范围字段有助于定位对象，但真正的访问权限仍须由宿主与存储服务核对。

这种设计给应用更多控制，也要求开发者承担更多工作：定义事实是什么、冲突怎样处理、何时读取，以及哪些字段必须精确保留。对于 R42，这些工作值得做，因为把未来规则误用到历史日期，会直接改变查询结果。

## 两个时钟：传播时间与业务生效时间

现在回到那条时区纠正。它至少同时涉及两种时间：记录什么时候到达模型，以及规则从哪个业务日期开始适用。

| 观察对象 | 内容 | 对任务的含义 |
| --- | --- | --- |
| 旧规则 | 上海时区，19 日之前适用 | 15–16 日窗口仍用旧口径 |
| 新规则 | 东京时区，自 19 日生效 | 下一周期采用新口径 |
| 旧提示快照 | 只看见上海时区 | 新任务可能还没取得新版本 |
| 新任务输入 | 规则、有效期与来源一起出现 | 模型可以解释本次选择依据 |

OpenCode 对持续指令来源保留观察到的内容哈希和更新事件，能区分旧时序与新来源；Deep Agents 的文件 memory 内容进入状态后，已有缓存键会阻止同一路径再次下载。这是两种实际不同的更新边界。不能假定重启进程必然刷新逻辑会话，也不能把某次规则文件重读当成全部长期记忆都已更新。

业务日期还需要独立处理。下面的两个等价示例只负责选择规则：有效区间采用“含开始、不含结束”，要求恰好命中一条，空缺和重叠都报错。示例使用规范的年月日字符串；真实应用还需校验来源、项目权限与日期格式。

```typescript
type Rule = { value: string; from: string; until: string | null };
const rules: Rule[] = [
  { value: "Asia/Shanghai", from: "2020-01-01", until: "2026-10-19" },
  { value: "Asia/Tokyo", from: "2026-10-19", until: null },
];
function selectRule(date: string): string {
  const found = rules.filter(r => r.from <= date && (r.until === null || date < r.until));
  if (found.length !== 1) throw new Error("rule gap or overlap");
  return found[0].value;
}
for (const date of ["2026-10-16", "2026-10-19"]) {
  console.log(`${date}=${selectRule(date)}`);
}
```
```python
rules = [
    {"value": "Asia/Shanghai", "from": "2020-01-01", "until": "2026-10-19"},
    {"value": "Asia/Tokyo", "from": "2026-10-19", "until": None},
]
def select_rule(date):
    found = [r for r in rules if r["from"] <= date
             and (r["until"] is None or date < r["until"])]
    if len(found) != 1:
        raise ValueError("rule gap or overlap")
    return found[0]["value"]
for date in ["2026-10-16", "2026-10-19"]:
    print(f"{date}={select_rule(date)}")
```

这段选择逻辑比“拿最新一条”多了一项约束，却让历史重跑保持原含义。即使执行发生在 19 日之后，R42 的业务日期仍会选中上海时区。

## 第一版该怎样取舍

个人助手只有少量稳定偏好，可以从精选文件与明确加载边界开始；资料增多后，把历史搜索与常驻偏好分开。不要为十条偏好先建一套复杂索引，也不要等到常驻文件无限增长才想起预算。

团队共享资料应优先确定权威来源、访问范围和修订方式，再决定是否增加向量索引。索引帮助找材料，不能成为谁都能改项目规则的旁门。异步整理适合降低维护负担，但应当保留候选、提交和生效状态，允许人检查重要变化。

对于 R42 这样的长任务，项目规则与执行状态分开保存。任务保留适用时区和依据版本，新规则保存未来有效区间；查询进度、日志位置与测试回执进入执行记录。恢复时先取得同一任务的业务日期，再组装所需规则。

核对记忆效果也应沿这条链：不在新任务里重复原话，观察能否取到正确对象与日期的版本；再检查实际查询参数。若文件正确而输入错误，修刷新或筛选；若输入正确而查询错误，继续修行动约束与结果验收。这样得到的改进比笼统地“换一个记忆模型”更有针对性。

现在，R42 和未来任务可以各用适用的规则。工程师眼下的问题仍是：“run-807 的 E42 到底对应哪个配置？”把事实保存下来之后，下一件事是给当前判断留下合适的依据。
