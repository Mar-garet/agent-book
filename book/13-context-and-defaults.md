# 第十三章：默认能力，是怎样被装配出来的？

本章只跟踪 Deep Agents 的 **一个构建入口** `create_deep_agent()`，观察它如何装配运行机制。返回图的执行、异步与流式入口不在这次构建入口计数中。再借 Pi 对会话与模型输入的处理，比较“保存了什么”与“当前提供什么”。

一个团队看到项目支持文件、Skills、记忆和子 Agent，便调用了最简单的构造方法。几天后，他们发现默认文件并不等同于本机目录，记忆来源还没有配置，子 Agent 也仍然能访问部分共享工作数据。

产品功能列表描述了可能提供的能力。真正运行的系统，还要经过构建、配置和本轮输入的选择。

## 先把装配者和执行者分开

应用开发者选择模型、附加工具、存储后端与必要的工作约定。构建入口据此组合一套图运行配置，再由底层执行系统处理消息与工具。

其中的 middleware，本书称为中间处理逻辑，是插在模型请求、工具执行或状态更新前后的处理机制。它可以加入说明、整理上下文、处理工具结果，也可能改变模型实际可见的能力。

构造时声明的参数，是装配输入。存储后端提供文件等能力的业务适配；检查点保存器与长期存储提供持久化基础。它们需要合作，但不是同一类对象。[Deep Agents 源码研究](../references/studies/pi-deepagents-execution.md)

## 从支持能力到实际生效，要经过几道选择

第一，项目是否实现了这种能力。第二，这次构建是否装配对应机制。第三，当前模型请求实际获得了哪些工具与内容。第四，结果能保存到什么范围、持续多久。

本次固定源码中，memory 与 skills 的构造参数默认都是 `None`，相应机制根据显式来源等条件加入。检查点和长期存储也没有由这个默认调用自动配置。我们不能把“支持跨会话记忆”直接读成“任何最小调用都已经持久保存”。

模型 profile，即针对特定模型的一组运行配置，也会改变装配结果。例如，这一版本的通用默认栈没有统一加入 TODO 规划工具，但某些模型配置会追加它。一本书若仅记住旧版本的默认工具列表，就可能把可选行为写成所有使用者都会遇到的行为。

这里限定的是这一个 Python 构建入口。命令行产品或其他上层应用可以另外传入默认参数，需要按各自入口核对。

## 文件接口不自动等于操作系统文件

没有指定其他后端时，构造器使用以图状态承载文件的后端。模型看到文件路径和读写工具，实际数据来自任务状态中的文件通道。

这个默认后端没有通用 shell 执行能力。其他后端则可以提供本地、远程或沙箱中的能力。文件中间层会根据后端能力调整实际暴露给模型的工具；最终工具清单需要在模型请求处确认。

这是一种有用的分离：上层用统一文件动作组织工作，具体存放位置由后端决定。与此同时，路径的含义、权限和寿命也必须随具体后端解释。一个叫作 `/AGENTS.md` 的路径，不会仅凭名字就自动指向当前电脑上的同名文件。

## 记忆会经过三个不同的位置

在本次 memory 路径中，程序先读取指定文件，解码后放进任务状态中的缓存，再在模型请求时加入系统消息。相关缓存键已经存在时，该读取路径不会再次下载文件。

因此，可以同时存在三份具有不同时间点的信息：文件里的新内容、图状态缓存的内容、已发出模型请求里的内容。修改第一份，不代表另外两份立刻变化。

这与前面讲过的 Hermes 启动快照不是完全相同的实现，但提出了同一个设计问题：**新事实从何时起参与下一次判断，失效与重新加载由谁触发？**

Skills 的常规路径先提供技能索引，再按任务读取完整说明；本版本也提供主动固定加载全文的选项。因此，按需加载是一种默认路径与配置选择，不能被概括成任何情况下都不装载全文。

## Pi 把原始会话与本轮输入分成不同视图

Pi 的会话管理器记录追加式会话树。编程会话根据当前分支、摘要与上下文编辑，构造运行时消息；再经过扩展上下文处理，转换为模型协议消息。

裸核心的处理顺序可以概括为：准备请求，变换应用上下文，转换成模型消息，再进行规范化。上层编程会话的拷贝与投影机制，不能自动推广为任意核心回调的保证。[Pi 投影研究](../references/studies/pi-deepagents-execution.md)

所以，排查“模型为什么忘了”时，应先找实际发出的请求，再沿投影、缓存和存档往回追。看到历史文件里还保留一句话，只能证明它存在于存档，不能证明这轮模型使用了它。

## 子 Agent 的隔离，需要逐项说明

Deep Agents 的默认 isolated 子调用会替换父会话消息，让子 Agent 从任务说明开始；同时，它还传入未被排除的其他状态，包括以状态表示的文件。子任务可以把允许返回的状态更新交还给父任务，并将最终结果整理成工具消息。

这使上下文隔离与工作产物交换可以同时存在。它并不自动创建一个权限独立、文件不可见的安全沙箱。

另一种显式 fork 模式会继承更多父上下文与配置；预编译子图又有自己的装配边界。比较多 Agent 时，需要把采用的模式和子类型写清楚，而不能只统计开了几个 Agent。

## 四个可以逐项核查的问题

| 要确认的事情 | 应当观察哪里 | 常见误判 |
| --- | --- | --- |
| 是否装配 | 构造参数与最终处理栈 | 把功能列表当作最小调用的默认行为 |
| 模型是否看见 | 实际请求中的工具与消息 | 把已注册能力当作已提供给模型 |
| 是否持久保存 | 后端、检查点、存储与读取范围 | 把一轮状态文件当作永久共享资料 |
| 是否隔离 | 子任务输入、工具、文件和返回更新 | 把消息隔离当作所有资源隔离 |

这些问题使比较从产品名称落到具体配置。它们还会直接影响恢复：一个动作完成后，结果究竟写进了哪个状态，下一次运行会从哪里重新获得它？

**本章练习：**画出一个 Agent 的文件、状态缓存与模型输入。分别改变其中一处，预测另两处会在什么时候改变；再为这个预测安排观察位置。
