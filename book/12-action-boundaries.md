# 可靠执行系统：让动作可控、过程可恢复、结果可核查

旅行草稿还在补齐，用户又提出一个要求：“行程改好先给我看，我确认以后，可以帮我加到我的日历。票和酒店还是不要订。”

这不是立即创建日程的许可。程序应先保存新的要求，等用户确认具体行程。接着用户又说：“先等等，我可能要改出发时间。”这时，助手究竟停什么、保留什么，恢复时又该问什么？

日历让问题变得具体。查询可以重复，日程创建过一次，再做一次就可能多出一条。运行程序需要分清还没发出的动作、发出后结果不明的动作，以及已经完成的动作。

## 让模型知道“等等”，与真的停下来不同

模型生成一次回复时，可能同时提出几项工具调用。程序可以全部检查后执行，也可以逐项检查，还可以并行处理。用户的新消息在什么时候进入模型，取决于这些安排。

Pi 被研究的核心路径会先执行这一批、收集结果，再在回合结束处读取排队的新指令。即使工具顺序执行，也不能想当然地认为两个工具之间一定读取新消息。

因此，“先等等”至少需要两种处理。程序把这句话放进后续模型输入，让模型知道用户改了主意；程序还要停止开始新的动作，而不能只等下一轮模型自行决定。

Pi 有独立的取消操作，具体工具是否及时响应仍看工具实现。Agent Framework 的工作流取消会取消并等待本地运行任务，失败时丢弃尚未提交的内部修改。这些机制能清理本地工作，但已经发给远端服务的请求仍需另外核实。

## 同一句暂停，在三个时点有不同后果

眼下的行程尚待用户确认，程序应停在创建日历之前。为了设计完整的暂停行为，还需要考虑用户在其他时点说“等等”会发生什么：

| 暂停时的实际情况 | 程序应该做什么 | 可以怎样告诉用户 |
| --- | --- | --- |
| 创建请求尚未发出 | 移出待执行队列，保存草稿 | 没有创建日程，等你确认新时间 |
| 请求已经发出，没收到明确结果 | 停止新请求，向服务查原动作 | 已停止后续操作，这一次是否创建还在核实 |
| 日程已确认创建成功 | 保存日程信息，询问后续处理 | 日程已经创建，暂停不会自动删除 |

这是三种可能情况，不是声称旅行任务已经分别运行过。用户改时间以后，程序要重新展示将要添加的内容，再取得确认；旧版本的同意不能直接用于新行程。

如果日程已经存在，删除或修改也是真正的动作，需要符合用户的新要求。把本地聊天标成“取消”，不会让日历里的内容消失。

    A[准备创建] --> B[确认内容]
    B --> C[发出请求]

## 一次允许，要对应这次真正执行的内容

“以后可以帮我加日历”是一项使用要求，“把刚才确认的周六上午行程加入我的日历”才指向较具体的动作。程序应保存用户确认的标题、日期时间、目标日历，以及确认之后有没有收到暂停或改动。

到执行之前，再比较一次这些内容。检查要决定这次请求能否开始。分工仍是：模型提出建议，程序核对用户要求，日历服务检查账号真正能做什么。

Codex 的命令调用会先确定目录与执行环境，判断政策、处理审批，再选择实际执行权限。OpenCode 根据动作和资源匹配规则。AgentScope 把允许、拒绝、等待确认变成不同运行状态。它们采用的规则不同，都给执行前检查留了位置。

工具参数合法也不够。日历接口接受一个正确格式的时间，不代表用户选了那个时间。Gemini CLI 的工具前钩子改过参数后，会重新判断政策；Cline SDK 在准备阶段合并输入与工具政策。先按旧参数批准、再按新参数执行，会让原检查失去作用。

## 并行能省等待，也会改变停止位置

查酒店和查返程互不依赖时，可以同时开始。先看返程结果再决定周日景点，就应保留这个先后关系。把所有操作并行，并不总能更快完成任务。

Pi 将请求准备、实际完成和回传结果的顺序分开；Hermes 会按读写安全对工具批次分段，让独立读取可以并行，修改跨过顺序屏障。它们都在安排哪些事情可以一起做，但不会替应用判断两次日历修改是否冲突。

对旅行助手，一个合适的起点是并行查询、顺序修改。新增、改时间、删除同一条日程，应让后一步知道前一步实际结果，否则可能在用户暂停时仍留下多个正在修改的请求。

## 没收到回执，不能记成“没有创建”

日历服务可能已经创建成功，网络却在返回时断开。助手看见超时，只能确认自己没拿到确定结果。

程序需要给“结果未知”一个正式位置：保存发出的内容，以及之后能向服务核对的操作标记；先查原请求是否完成，再决定要不要重新提交。操作标记是用来识别“刚才那一次”的小标签，下一章会具体解释它怎样防重复。

browser-use 的动作历史重放会再次执行浏览器动作，不能把重新点一遍当成单纯恢复观察。OpenHands 前端重连恢复的是事件显示，后端动作是否执行仍由后端回答。界面重新连接、程序重新运行、日历是否已经改变，是三件事。

## 保存了进度，也可能重做动作

检查点是程序保存下来的执行进度，例如“资料已查完，正等用户确认”。它帮助重新开始后找回位置，却不自动和日历服务一起提交。

本书用真实 LangGraph 和模拟服务运行过四种独立小场景。创建记录后在同一节点等待，恢复会重复创建；把创建和等待拆开，无额外故障时只创建一次；服务认出相同操作标记时，两次请求保留一条记录；创建成功、节点返回前失败，即使拆开仍可能再创建。

这说明要同时处理两件事：程序保存哪些步骤，服务怎样识别同一个动作。只做好一边，还不足以解释另一边发生了什么。

OpenCode 保存执行记录后可以在重新启动时继续，但也允许一段工作再次执行，开发者要容纳至少一次执行的情况。OpenClaw 在已经有外部修改或交付证据时，会限制继续换候选重试。它们都强调保留已经发生的事实，避免把再次尝试误当作从未执行。

## 第一版应该留下哪些记录

旅行助手不需要一开始就建设复杂平台。先把几件事保存清楚：用户最后确认的行程、当前是否暂停、哪些请求已经发出、日历返回了什么、还有什么没核实。

模型可以提出添加，程序根据保存的确认决定是否允许，适配器调用日历，服务返回结果，程序再读日历核对。这里的适配器，是把应用请求转换成日历接口调用的代码。它应明确区分“查询已有日程”和“新建日程”。

恢复时先读这些记录，核实结果不明的动作，再决定下一步。用户曾说“先等等”，就重新确认要添加的具体内容，不应仅因为程序重新启动而继续创建。

现在，暂停不再只是一句回复：尚未发出的请求能停住，已经发出的请求有地方核查，已经创建的日程也不会被假装取消。下一章继续看那个最窄的空隙：服务已经创建，程序还没存下结果时，重新运行怎样避免第二条日程？
