# 第十六章：同一个 MCP 服务，为什么进入两个 Agent 后表现不同？

本章按模型能够实际点名调用的工具计数：Goose 常规路径有 N 个已暴露扩展工具，Cline SDK 路径有 M 个已注册并保留的工具，数量随目录和策略变化。目录缓存和工具描述不另算模型入口。Goose 的可选代码模式（Code Mode）另提供三个能力发现与代码执行入口，同时仍可能保留其他工具，不能把三个当作整个系统的工具总数。

假设两个助手连接同一日志服务。一个先让模型寻找工具、查看详情，再执行查询；另一个直接把每个查询工具及参数交给模型。服务一样，模型经历的工作过程却不同。

MCP 约定了能力交换方式。宿主仍然要决定如何组织这些能力，怎样控制输入和结果，以及怎样把失败带回下一轮。

## 先把比较范围限定清楚

Goose 的案例沿扩展工具目录与调用路径展开。Cline 的案例限定为当前仓库中的 SDK 主线，不把同仓库的 VSCode 宿主实现全部视为 SDK 默认行为。

同一仓库可以容纳多个入口、多个产品和不同的工具管理方式。比较时先写下实际走的是哪条路径，往往比先统计功能更重要。[源码研究与固定版本](../references/studies/goose-cline-mcp.md)

## 能力需要一个在宿主内唯一的身份

两个 MCP 服务都可以声明一个叫作 `search` 的工具。宿主要让模型区分它们，同时保留正确的路由关系。

Goose 为常规工具加上扩展归属前缀，并在目录中保存模型名称与服务原名的对应。Cline SDK 为各个服务工具生成模型工具对象，必要时清理、缩短名称并加入区分信息；其调用闭包仍持有服务原名。

名称在这里承担身份与路由职责。一个名称看起来更整齐，并不代表业务权限更明确；业务范围仍由工具与宿主策略确定。

## 定义预算与结果预算，需要分别安排

工具定义告诉模型有哪些能力，以及如何填写参数。工具很多时，这些说明本身就占据输入空间。

Goose 的可选 Code Mode 把一部分细节改为逐步发现：先看名称和简要说明，需要时再取完整结构，再通过代码调用具体能力。它改变的是能力如何进入上下文；配置条件和保留工具仍需要逐项核对。

Cline SDK 本轮核对的主线，会把筛选后的服务工具逐个转换成模型工具。宿主可通过显式策略关闭无关工具，模型前处理也可改变本次请求，但不能仅凭这些扩展点就认定已经采用同一种按需发现方式。

上述做法各有成本：直接提供详细定义，可能减少发现步骤；逐步发现可能降低初始占用，也可能增加往返。本轮没有测量二者的 token、延迟和成功率。

工具结果则发生在调用之后。Goose 和 Cline SDK 都有把过大结果放到外部、交给模型预览与读取位置的机制。这处理的是结果体积，不能代替对工具定义数量的控制。

## 临时结果缓存，不等于长期保留的原始记录

在所核对的 Cline SDK 路径中，过大结果可以进入会话文本缓存，模型获得预览与可分段读取的位置。缓存有容量和迭代清理规则，内容可能后来失效。

这时，模型看见的文本、缓存里的完整结果和真实服务中的业务状态，又是三个不同位置。缓存失效后，重新执行读取通常只是再次获取信息；重新执行写入则可能造成重复效果。

该实现的缓存未命中提示也提醒调用者，不应通过重复有副作用的操作来找回输出。系统要保留动作标识和结果查询路径，让“重读结果”有独立方式。

## 工具目录变化，在哪一层变成了新能力

MCP 服务增删工具后，客户端可能收到通知，宿主缓存也可能过期。但模型真正看到新工具，还要经过目录获取、工具对象重建和请求准备。

Goose 使用版本与作用域来判断目录缓存是否仍有效，同时在一次推理准备中持有对应目录快照。新目录的出现，不应悄悄改变一项已经准备好的调用所指向的执行者。

Cline SDK 中，一次工具列举会生成一组工具闭包；目录缓存的 TTL 并不能独自证明当前 Agent 的模型工具表随之更新。其 VSCode 宿主另外有变化通知与刷新实现，但两者之间的完整接入时机仍需沿具体调用链证明。

| 所在层次 | 这一层确认了什么 | 还不能直接推出什么 |
| --- | --- | --- |
| 协议客户端 | 服务发布了变化 | 所有调用都已采用新目录 |
| 宿主目录缓存 | 新目录可以被读取 | 当前 Agent 工具对象已重建 |
| Agent 注册表 | 当前可用工具集合 | 本轮模型已经看到它们 |
| 模型请求 | 本轮提供的能力 | 已准备动作可以改用别的执行者 |

这也是一种时间一致性问题：既要及时看到变化，又要让正在进行的调用保持清晰的身份。

## 元数据如何影响决策，由宿主决定

Goose 的一个智能审批模式会消费服务给出的只读提示，结合用户显式规则作决定。这条链使用了服务的描述，但没有因此验证服务实现真的不会写入。

Cline SDK 本轮核对的转换链没有把这组 MCP 注解保留到相同的工具描述对象中，自动批准由其宿主策略与审批回调控制。这个事实不能推广为整个 Cline 产品都忽略注解，也不能由此给两者作总体安全排名。

比较的具体问题应当是：哪个来源提供信息，哪个组件采用它，影响的是模型选择、审批提示，还是实际可执行范围？

## 错误需要跨过不止一层表示

服务可以正常返回一份“业务失败”的结果。宿主还可能因为连接异常而没有获得服务结果。协议调用完成、包装函数返回和业务动作成功，仍是不同判断。

Goose 在整理对话工具结果时区分这些情况。Cline SDK 的该包装链则可能将服务返回的业务错误对象留在输出内容中，而不直接提升为 Agent 外层错误标记；具体模型适配器怎样展示，还需要实际实验。

因此，统计工具成功率之前，应先写清成功读取的是哪一层。否则，接通服务和完成目标可能被记成同一件事。
